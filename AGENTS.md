# Using Vite+, the Unified Toolchain for the Web

This project is using Vite+, a unified toolchain built on top of Vite, Rolldown, Vitest, tsdown, Oxlint, Oxfmt, and Vite Task. Vite+ wraps runtime management, package management, and frontend tooling in a single global CLI called `vp`. Vite+ is distinct from Vite, and it invokes Vite through `vp dev` and `vp build`. Run `vp help` to print a list of commands and `vp <command> --help` for information about a specific command.

Docs are local at `node_modules/vite-plus/docs` or online at https://viteplus.dev/guide/.

## Built-in Commands vs Scripts

`vp <name>` runs a built-in command. `vp run <name>` runs a `package.json` script or a `vite.config.ts` task. Scripts cannot overwrite built-ins, so `vp dev` and `vp run dev` may do different things. Check `package.json` and `vite.config.ts` first, and run `vp run <name>` when the project defines a script or task with that name.

## Tool Versions

Run `vp toolchain` to show versions and relationships in the active Vite+
release. Add a tool name to select part of the graph. For example, run
`vp toolchain vite`. Use `--global` to ignore the local `vite-plus` package. Use
`vp why <package>` to show the package-manager dependency graph.

## Review Checklist

- [ ] Run `vp install` after pulling remote changes and before getting started.
- [ ] Run `vp check` and `vp test` to format, lint, type check and test changes.
- [ ] Check if there are `vite.config.ts` tasks or `package.json` scripts necessary for validation, run via `vp run <script>`.
- [ ] If setup, runtime, or package-manager behavior looks wrong, run `vp env doctor` and include its output when asking for help.

# effect-actions

Library: `@gjermundgaraba/effect-actions`. Define Effect action contracts once and project them
onto HTTP, MCP, native Toolkits, and CLIs. Vocabulary: [docs/CONTEXT.md](docs/CONTEXT.md).
Use [lint policy](CONTRIBUTING.md#lint-policy) for lint decisions,
[documentation rules](CONTRIBUTING.md#documentation-rules) when changing docs,
[test rules](CONTRIBUTING.md#tests) when writing tests,
[design notes](CONTRIBUTING.md#design-notes) (one file each in `design/`) when revisiting recorded decisions,
and [release instructions](CONTRIBUTING.md#release) when releasing.

## Repository map

- `src/<domain>/`: `contract`, `authentication`, one folder per surface (`http`, `mcp`, `rpc`, `toolkit`, `cli`), `testing`, and `stdio`, the stderr console of stdio servers and CLI commands, which has no public module. Each holds its PascalCase public module, a package subpath, beside the lowercase private files it owns ([Domain folders](design/domain-folders.md)).
- `examples/`: runnable, type-checked and linted programs. Several are compared byte-for-byte with doc snippets.
- `tests/<domain>/`: Vitest suites plus `*.spec.ts` compile-time assertions, checked by `vp check`, mirroring `src/`. `tests/guarantees/` holds rules every surface keeps, `tests/support/` what is not a suite: a helper, or a script a suite runs.
- `docs/`: consumer reference for agents, one card per module (`API`, `Canonical`, `Rules`, `Failure modes`). Rules that hold on every surface live once, in `docs/guarantees.md`; cards link to them. `CONTEXT.md` is vocabulary. No page names a `src/` path: `docs/` ships as the skill.
- `design/`: design notes, one recorded decision per file, indexed in `CONTRIBUTING.md`.
- `skills/effect-actions/`: a copy of `docs/` generated by `vp run docs:sync`. Never edit by hand.
- `scripts/`: package-consumer fixture, tarball test, skill generator.
- `tools/oxlint/`: the vendored anti-slop plugin, the repository's `no-comments` rule, and their regression tests.

## Commands

```sh
vp check            # format check, type-aware lint, type check; read-only (--fix writes)
vp test             # all suites, including docs and skill sync; writes transient lint probes in tools/oxlint/tests
vp run test:package # builds dist/, then type-checks and runs the tarball in an isolated consumer
vp run docs:sync    # regenerate the skill after editing anything in docs/
vp run example      # the authenticated example server on 127.0.0.1:3000
vp run build        # module-preserving ESM and declarations in dist/, one entry per public module
vp run dev          # watch the library build
```

## Validation

The Vite+ block above is regenerated by `vp config` (run by `vp install`); do not edit it. Where it conflicts with the rules below, the rules below win.

- For code or tooling changes, run focused checks during iteration. Before completion, run full validation: `vp check`, `vp test`, and `vp run test:package`. During concurrent work, coordinate one final run after changes settle.
- For prose-only changes, run relevant formatting, documentation, and skill-sync checks. Treat changes to executable examples or snippets as code changes.
- For read-only reviews, run checks needed to support the assessment; dependency installation and commands that write must follow the isolation rule below.
- Fix failures introduced by the change and rerun affected checks. Report unrelated failures and checks not run; do not claim full validation when it was incomplete.

## Invariants

- Contracts (`Action`) never import transport code. Each surface owns its own mapping from actions to itself and validates only the names it serves.
- `src/contract/` holds what every surface shares: name checks, the nominal `Implementation`, builders as memoized layers, authorization and dispatch, the built-in errors and the call rule every client shares. A domain may import another's private module, never another surface's public one, and `src/contract/` imports nothing outside itself; source imports source by relative path, never by the package's name, and `no-restricted-imports` in `vite.config.ts` reports all three. Public modules re-export the types consumers need, named `Options` for a module's main function, `<Function>Options` for another's, and `Any` for its erased value.
- A contract states who may call it: `caller: Action.Anyone` or the identity service a caller must have. A surface enforces that identity through a named authentication descriptor (`Authentication.make`) and its provider (`Authentication.layer`), plus discovery metadata; verification, login and consent stay in the application. Action-level authorization is the `authorize` each implementation of protected actions states: the application writes its rule, and the library runs it but writes none (`Action.allowAll` permits every authenticated caller). Operational limits, such as a rate limit, are the handler's, failing with errors the contract declares; record-level checks belong in the handler's data access.
- A browser client imports `Action`, `ActionHttp`, `ActionRpc` and `Authentication` (a binding names its authentication descriptor): they and the modules they import use nothing specific to Node or a server platform, and import Effect only through `effect`, `effect/http`, `effect/http-api` and `effect/rpc`, as `tests/browser.test.ts` checks.
- Build on Effect's native servers and clients (`HttpApi`, `McpServer`, `RpcServer`, `RpcClient`, `Toolkit`, `Command`). Add no protocol runtime.
- Build-time and request-time requirements stay separate in the types. Never provide request identity at a server's startup, in code or in docs. In memory, `Action.client` takes its caller per call; under `Testing.layer`, the routes keep their real authentication, and each client sends its caller's credential.
- Public behavior changes update the matching `docs/` page in the same commit, then `vp run docs:sync`.
- Doc snippets that are also examples stay identical to the example file; edit the example first.
- Use the Effect release pinned in `package.json`. Check `node_modules/effect` before assuming an API shape.
- Follow the lint policy in `CONTRIBUTING.md`: refactor the cause, and never launder a finding.

## Direction

- Optimize for a clean, consistent, powerful API with minimal consumer boilerplate. Judge changes by what consumers must understand and write.
- Prefer one obvious way to perform each task. Avoid overlapping entry points, aliases, and competing patterns for the same purpose.
- Make the common case complete with useful defaults and minimal setup. The library handles mechanical wiring; applications supply their domain behavior and policy.
- Make advanced capabilities optional and discoverable. Extend the same concepts through consistent options and native Effect composition, keeping ordinary usage free of advanced configuration.
- Prefer native Effect behavior to custom machinery. Check the pinned Effect APIs before proposing a helper, and treat a restriction that blocks useful native behavior as a defect.
- A new public concept must justify its learning and maintenance cost. Show the concrete need, why existing concepts cannot serve it cleanly, and what complexity it adds or removes. An additional export or option is not necessarily an additional concept.
- Assess simplicity across the complete consumer workflow. Removing a helper is not an improvement if every consumer must rebuild it.
- Breaking changes and churn are fine. Never add compatibility shims, deprecations or migration aliases.
- Proposals and options that change the public API or consumer workflow show consumer code before and after, and say which concepts appear or disappear. Show the common case and, when affected, one advanced case. Explain how consumers move between them without adopting a different model.
- Do not reverse an earlier decision, recorded in a design note (`design/`) or the `CHANGELOG.md`, without naming it and saying why.
- When a documented guarantee lacks coverage, determine whether it is intended and valuable. Test intended guarantees; correct accidental or unsupported promises. Do not build machinery merely to preserve an accidental claim.

## Several agents share this worktree

- Reviewers leave the shared worktree untouched. Dependency installation, builds, tests that write repository fixtures, scratch files, and mutation tests run in an isolated copy containing the changes under review, including relevant uncommitted changes. Clean up only what you created.
- The git stash is shared by every worktree of this repository. Never run a bare `git stash` or `git stash pop`.
- Commit only when asked. The pre-commit hook runs `vp check --fix` on staged files: expect reformatting, and failures from other agents' unfinished edits.
- Rerun a test that timed out under load on its own (`vp test <file>`), and report both results.
- Report a skim as a skim. A plan step is done only when it was done in full.
