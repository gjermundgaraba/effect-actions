# Contributing

For people and agents changing the library. Consumers read [docs/](docs/README.md) instead.

## Setup

Requires Node.js `^22.18.0 || ^24.11.0 || >=26.0.0` (`devEngines` in `package.json`; CI tests 22, 24 and 26) and [Vite+](https://viteplus.dev). Run `vp install`, then see
[AGENTS.md](AGENTS.md) for the commands, the repository map, and the validation rules.

Vocabulary: [docs/CONTEXT.md](docs/CONTEXT.md). Use its terms in code comments, docs, and tests.

## Documentation rules

- `README.md` sells the library to humans: the pitch, one showcase snippet, why, install, links. No reference material.
- `docs/` is for coding agents. Each public-module reference card has the same sections: **API**, **Canonical**, **Rules**, **Failure modes**. State what holds and what breaks, without tutorials or narrative. Routing, setup, vocabulary, and shared guarantees use the structure their role needs.
- `docs/README.md` is the routing table and doubles as the skill body. One line per page saying when to read it.
- A change to public behavior changes the matching `docs/` page in the same commit. Then run `vp run docs:sync`; `tests/skill.test.ts` fails if the generated skill is stale.
- API sections inventory exports and options; do not hand-copy complex generic declarations. Exported TypeScript declarations are the exact signature reference.
- `tests/docs.test.ts` compares the README showcase and selected executable examples with files in `examples/`, so those snippets stay type-checked. Edit the example, then paste. Compile-only tests assert public API behavior directly, without maintaining a second type definition.
- `docs/CONTEXT.md` defines terms. Add a term there before using it in docs.
- A rule that holds on every surface lives once, in `docs/guarantees.md`. A module card states what is its own and links there; a restated rule drifts.
- Docs describe behavior, not the code: no page names a `src/` path, and `tests/docs.test.ts` checks it. Implementation rationale belongs in code comments or below.
- Tests assert this library's behavior. Effect's or MCP's own wording is matched by its stable fragment (`toContain('at ["value"]')`), never in full, unless a doc quotes it. A test of Effect's own behavior stays only when a doc promises that behavior: the 415, CORS preflight, the generic MCP defect text.
- Every file in `examples/` is listed in `examples/README.md`, which `tests/docs.test.ts` checks; `docs/README.md` links there rather than keeping a list of its own.

## Design notes

- HTTP input is strict through `HttpApi.PayloadParseOptions` alone. A strict `ParseOptions` would also govern error encoding, where it could turn a declared error into an empty 500. Only `layer`'s own API carries it: a client encodes with Effect's default, dropping a field the input does not declare, as TypeScript lets a wider value through. This reverses 0.8.0, whose typed clients failed with `SchemaError` before sending such a call, one the compiler had accepted. An action without input is `Schema.Record(Schema.String, Schema.Never)`: `Schema.Struct({})` accepts any value but `null`, and has no object root for MCP.
- MCP over HTTP serves 2026-07-28 only. The stateful revisions work over Effect's HTTP transport, and request identity stays per request, but each `initialize` registers a session that Effect's runtime never deletes, with no expiry and no `DELETE` termination, and any caller holding the session id may use it.
- MCP stdio keeps the stateful revisions, 2025-11-25 back to 2024-11-05, until hosts speak 2026-07-28. Measured on 2026-09-29 against Claude Code 2.1.284 and Codex 0.159.0. Both open stdio with `initialize` (2025-11-25 and 2025-06-18), so neither connects to a stdio server that serves 2026-07-28 only. Codex also opens HTTP with `initialize`, so it cannot connect to `layerHttp` at all.
- A success is sent as it is, never wrapped. 2026-07-28 carries any encoded success as `structuredContent`, a bare number, string, array or `null` included, with its JSON as text, and Claude Code accepts all of them. On the earlier revisions Effect's adapters decide, not our code: 2025-11-25 and 2025-06-18 structure, and list an `outputSchema` for, only an object; 2025-03-26 and 2024-11-05 structure nothing; a success they do not structure is text alone, a string as itself. This reverses the earlier decision to keep the `{ value }` envelope while stdio serves the 2025 revisions: 0.8.0 already shipped bare successes, and a downstream app documents them, so the envelope would wrap them again now and unwrap them again when those revisions go. The Python SDK rejects a `null` `structuredContent` (python-sdk#3345); that is the SDK's bug.
- A text field is an option of the MCP server, `tools: { readPage: { text: "markdown" } }`, keyed by action name like `ActionCli.make`'s `commands`, not 0.8.0's `mcp.text` on the contract: a contract holds no surface's options, as `Action.make`'s `mcp` became `hints`. Native `McpServer.registerToolkit` builds every listing and result with the whole success as structured content, so `ActionMcp` registers the toolkit on a copy of the registry whose `addTool` removes the field from the tool's listed `outputSchema` and its `required`, and wraps the tool's handler: a success whose field holds a string is sent as that string, raw, then the JSON of the rest, which is the structured content. Every other result is the native one, so decoding, failures and defects stay native, and each revision's adapter projects the split result as it projects any. A field that is not a top-level property of the listed schema fails the layer build rather than publish a schema the structured content would not satisfy. The types accept only a top-level string field of a struct success, where 0.8.0 let a union's through to that failure; an erased success may name any field. `Testing.mcpClient` takes the same `tools` and puts the first of two text blocks back under the field before decoding, reading only the entries of the actions it calls, so one constant serves the endpoint and every client that calls one of its actions. A client that calls none takes no `tools`: TypeScript refuses an object that shares no key with a type whose keys are all optional. A native option would delete the copy.
- A request's own value wins over a startup value under the same tag, on every surface. `HttpApiBuilder.group` and `McpServer.registerToolkit` apply the context they are built in on top of each request's. So `ActionHttp.layer` builds its group in an empty context, where the group finds only its `HttpApiMiddleware`, and a route middleware of each layer runs its routes over `Context.merge(startup, request)`, without the layer's `Scope`. `ActionMcp` registers its toolkit with only the registry and the tool handlers; `Toolkit.handle` already puts each handler's build context beneath the call. Both rely on those functions reading nothing else from their build context: a service they start to read fails the layer build, but a reference would silently take its default. Re-applying the identity inside the shared dispatch was rejected: a Toolkit call a handler makes under a narrower identity would run as the signed-in caller. The merge wraps the whole route rather than the handler call, so `HttpApi`'s own error reporting runs once, in the merged context.
- `ActionHttp` routes take only JSON-typed requests. The same route middleware answers a request without a content type with 415 before `HttpApi`'s default reads it as JSON, so every POST a page can send without a CORS preflight (no type, `text/plain`, the form types) is a 415, and cookie credentials cannot drive a cross-site write. As on the MCP endpoint, the check runs after the middleware around the layer.
- `Authentication.make` returns Effect's own `HttpRouter.Middleware`, not a finished layer, because only middleware composes: with `.combine`, a service resolved per request, such as a tenant, can feed authentication, and middleware reading the identity can follow it. Its second argument is always a builder, as `implement`'s may be. A per-request Effect and a builder are both Effects and cannot be told apart, so an authentication without startup services is `Effect.succeed(authenticate)`. What the builder yields is the layer's, built once per layer graph; what the per-request Effect yields is each request's, never captured from startup. Discovery is registered in the middleware's build, so every composition publishes it.
- Request body size is host configuration, not a library option: the host provides `HttpServerRequest.MaxBodySize` to `HttpRouter.serve`'s layer. It is Effect's server-wide setting and covers every route, the host's own included; an option per surface would duplicate it for only some of them. Node's server drops an over-limit request without a response. A web handler ignores the setting, so its platform limits bodies.
- TypeScript 7 or newer only. The package is type-checked on the pinned TypeScript 7 alone, and adds no signature workaround for an older compiler's inference.
- `implement` infers what each handler owes into one map, `R`, reverse-mapped from a list's record key by key (`Several`), and `RS` for one action's handler; plain handlers and builders take the same path. So a handler is typed from its contract however it is written, unless its builder reaches `implement` through `.pipe(...)` or an overloaded wrapper such as `Effect.withSpan`: TypeScript gives the Effect before `.pipe` no contextual type, and types an overloaded call's arguments from its first overload. The record was once inferred whole, as `H`, and checked afterwards (`Exact`): a generic handler, such as one `Effect.fn` makes, then had no contextual type and took an `any` input, where 0.8.0's `group.implement` had typed it. A list takes no single handler, which `NoHandler<R>` states. It must stay a named alias: while a builder's inner generic call, such as `Effect.gen`, is inferred, an alias's type arguments keep TypeScript's mark that they are not yet inferred, where `never`, or the same object type written inline, becomes a real candidate and the builder's record loses its contextual types (`examples/handlers.ts` then fails with TS7031, as the specs do). One action's handler and a built hook are the reverse, and must stay written out rather than `Handler<T, RS>` and `Before<A, RB>`: an alias carrying `RS` or `RB` before they are inferred bears that mark as a whole, so an `Effect.fn(...)` that a builder, or an Effect building the hook, returns would infer nothing from it and take an `any` input or action (the specs' `@ts-expect-error` pins then go unused). One action's `R` is constrained to `never`, so a record keyed by its name is refused, and a list's record must have a key for every action. Reverse-mapped inference costs instantiations superlinear in a record's size: measured on TypeScript 7.0.2, one `implement` of 60 actions adds 59k instantiations (25k before), of 150 adds 255k (62k), of 300 adds 869k (124k) and 0.2 s.
- `implement`'s build channels are `Deferred<T>`, `[T][T extends unknown ? 0 : never]`, rather than `NoInfer<T>`. Either keeps an implementation written inside a surface's arguments from inferring them from the surface's parameter, where they would be `unknown`. `NoInfer<A | B>` also survives into a layer's requirements, where providing `A` and `B` in two `Layer.provide` calls leaves it owed, and shows in every hover; `Deferred` reads as `A | B` once inferred.
- Every `implement` states its hook; `Action.allowAll` is the hook without an action-level rule. This reverses "Omit it for a public implementation", the rule since the hook's introduction (09051f7, then ca08c38, and 48c55a3, whose `before?` also accepted `undefined`). An omitted hook meant no authorization: an implementation split off after authorization existed compiled and served its writes to every authenticated caller, and an admin write that reads no identity compiled with neither a hook nor authentication. A required hook follows `access` (fe492ed: an action nobody classified fails to compile instead of defaulting to the dangerous side) and `share` (9b95d84: serving fewer actions never drops authorization). `implement` also throws for a missing hook, for plain JavaScript and for one `undefined` at runtime, as through an import cycle. The cost is one argument per implementation without a rule, the quickstart's included.
- A hook may be built by an Effect, as handlers are, and each implementation keeps its hook in a memoized layer of its own beside its handlers': a share keeps its source's handlers and replaces only the hook. `Effect.isEffect` tells the two forms apart, as it tells a builder from a handler, so an `Effect.fn` hook stays plain, and a service whose value is a hook is an Effect building it once per layer graph for every implementation it guards. A built hook's own state is per implementation; state shared across implementations belongs in a service.
- A hook fails with a refusal, or with an error every action of its implementation declares: `Refusal | CommonErrors<A>`. This partly reverses d72a2f8's "One `before` hook, failing with a refusal", which narrowed the hook as a side effect of replacing group and surface `errors` lists with the built-in errors, while the hook was still typed over `Action.Any`, and restores 09051f7's rule: the hook fails with what every action declares. No error list returns. Each action declares the error in its own `errors`, which every surface declares for it and every client decodes, so a limit such as `RateLimited` reaches MCP, the Toolkit and the CLI as a typed error, and an action added without it does not compile. A wrapper must be applied to every handler of every implementation, and a handler left unwrapped leaves its action unlimited; the hook is written once for every action of its implementation and runs on every surface. Only a refusal steps up. `CommonErrors` keeps each member of the actions' declared errors that no action leaves out, one at a time. An intersection of each action's union, inferred contravariantly, multiplies them out: TypeScript refuses it as too complex (TS2590) from 11 actions of 3 errors, or 9 of 4, even for a hook that only refuses. Filtering every declared error against every action costs their product, so `implement` and `share` filter only one action's errors, among which is every error all the actions declare (`CommonErrorsAmong`): the first listed, or, for a list whose type fixes no first action, such as an array without `as const`, `Object.values(...)` or `[...actions, extra]`, one member of the union of its actions (`OneOf`). Letting such a list's hook only refuse would cost less, but would refuse its limit. `OneOf` infers the member from thunks returning a `Carrier`, an interface holding its type argument without using it, which TypeScript relates without comparing what it holds. Thunks returning the actions themselves are compared pair by pair: one `implement` of 1000 actions took 3.2 s more than on ee1cb78, and one of 1400 from `Object.values(...)` was too complex to compare (TS2859), where ee1cb78 compiles it. Measured on TypeScript 7.0.2 with `Schema.TaggedError` classes, one `implement` of 150, 300, 400 or 1000 actions, each declaring three errors of its own and a shared one, adds 9k, 18k, 23k or 57k instantiations to the 0.60M, 1.72M, 2.77M or 14.10M it costs without a hook's errors (ee1cb78) when its list is a tuple, 19k, 38k, 50k or 125k when it is not, and at most 0.3 s. Filtering every declared error more than doubled the instantiations at 150 actions and added 0.4 s, added 1.8 s at 300, and made 400 actions of three errors, 300 of six or 700 of one too deep to check (TS2589), where ee1cb78 compiled 1000. An erased action's errors are `unknown`, which admits nothing, wherever it is listed, so `Action.Before<Action.Any>`, `Action.allowAll` included, only refuses and fits every implementation. `implement` and `share` also keep the plain hook written out for this: TypeScript relates one `Before` to another by the variance it measures for their actions, which does not see through `CommonErrors`, so a hook typed over an action with wider `errors` would pass there. `Before` keeps the full filter: through `CommonErrorsAmong`, TypeScript measures a variance by which `Action.allowAll` no longer fits a `Before<A>`. That leaves one ceiling, a hook annotated `Action.Before<A>` over many actions: over 300 actions of three errors of their own it adds 2.9M instantiations and 1.8 s, and over 400 it is too deep to check. Such a hook is left for `implement` to type, or annotated `Action.Before<Action.Any>` when it only refuses. A limit before decoding, over HTTP only, stays router middleware with the binding's `errors`.
- A Toolkit tool's `id` carries the key of what runs a call, its implementation's handlers' builder and hook, from a `WeakMap` private to `ActionToolkit`, because Effect finds a tool's handler by its `id`: the `layer` of any `make` call serves any `toolkit` of the same implementations, and of an `Action.share` of one that keeps its hook, which has the same builder and hook, while two implementations with tools of one name, such as one and an `Action.share` of it behind another hook, never run each other's handlers. Keyed by the implementation object, a share keeping its hook, an agent's fewer tools, took a layer of its own and isolated nothing: given its source's layer, which the types accept, its first call died on a missing handler. This revises the unreleased key per `make` call, a `Handled` service in 4ba23d1 and an id suffix in b0dc80a, and keeps their stated purpose, each toolkit's handlers its own beside another's with tools of the same names: since the hook moved from a `make` option onto the implementation, a `make` call separates nothing its implementation does not. Keyed per call, a toolkit and a layer of one implementation from two `make` calls type-checked, as `Tool.HandlersFor` is keyed by name, and the first tool call died on a missing handler, so toolkits made per agent or per approval policy could not share one handler layer. Lost: two layers of one implementation, built apart with different services and provided together, each served its own toolkit; now one serves both. Separate services take separate implementations.
- Each call has a scope of its own, opened by the shared dispatch around the hook and the handler, and `implement` and `share` leave `Scope` out of the request map, so no surface handles it: the CLI's own `Effect.scoped` and its `Exclude` are gone. A Toolkit call held what it acquired until its caller's scope closed, called directly or approved through `LanguageModel`, which runs an approved call in its caller's scope: with a pooled connection per call, a third call on a pool of two waited forever. `runStdio`, each tool and `generateText` also required a `Scope` nothing used. MCP and HTTP already released per call. Opened in dispatch rather than around tool calls alone, the scope covers HTTP too, where a call's finalizers now run before the route middleware resumes and before the success is encoded, not when the request's scope closes; action codecs are service-free, so nothing after the call reads what it acquired. A resource that must outlive a call is the builder's, or a service the host provides around its calls.
- `needsApproval` is one check over every call, `(call, context) =>`, whose `call` is a union by action name, so checking `call.name` narrows `call.input`. This reverses the unreleased per-action option, a function of each action run once by `make` (0a99a00) returning its tool's native approval (0db3f3a), whose input was the union of every action's: `action.name === "erase" ? ({ hard }) => hard : false` did not compile. A record keyed by action name would narrow too, but a rule over every action, such as `call.action.access === "write"`, would then take an entry per action; one check states both. It returns the native `boolean | Effect<boolean>`, requiring nothing: `LanguageModel` runs it in the caller's context, so it reads the caller with `Effect.serviceOption`, and a policy per caller needs no toolkit per caller. `LanguageModel` reads a failed check as no approval needed (`Effect.orElseSucceed(constFalse)`); the error channel stays `never`, so a check decides what its failure means rather than failing open unseen.
- A CLI command fails with Effect CLI's `CliError.UserError`, whose `cause` is the action's failure and whose message is the JSON HTTP sends for it: `Command.run` prints it on stderr and marks it reported, so a program runs on the stock `NodeRuntime.runMain`. This reverses fe492ed's "A CLI encodes nothing, so it declares no errors", and retires the reporting block the examples carried since cd08952 (aa09f83 its last form): a command's own failure reached `runMain`, which printed it on stdout with a stack and none of its fields (a not-found error's `id`, a `Forbidden`'s `scopes`), and the block moved that report to stderr but still lost the data. Input that does not decode is `InvalidInput`, and the process exits with the cause's `Runtime.errorExitCode`. `Failure` is exported as a type only: `instanceof` an exported generic class narrows `Command.run`'s error to `Failure<any>`, whose `cause` is `any`, where `error.cause instanceof X` is typed. A failure no schema encodes, a builder's or the transport's, prints as its tag, or an error's name, and its message, and each cause's, never its other fields: a message alone dropped the refused connection beneath an `HttpClientError`, and a builder's error may hold a connection string. It is built by hand rather than with `Cause.prettyErrors`, which prints a failure that is not an `Error`, a plain object or a `Data.TaggedClass`, as its JSON, every field included, and it reads no plain object's `name`, which may be a field like any other. A success that does not encode is a defect, as it is an empty 500 over HTTP, reversing the typed `SchemaError` since cd08952: the handler broke its contract, and a typed failure read as the caller's mistake. Rejected: the library printing each failure and marking it reported itself, which a host could neither restyle nor switch off, as `CliOutput`'s formatter and `renderErrors: false` do for a `UserError`, and which would mark the host's own error objects.
- What a command runs, its builder, hook and handler or its client call, gets the console `runStdio` gives its program, since a CLI's stdout carries data as a stdio server's does: every logger and `Console` method writes to stderr, `Logger.consoleJson` and `Console.log` included, which `Logger.LogToStderr` does not move. It reaches only what the command runs: `runMain` reports a defect, and a failure of a layer the host provides, outside the program with the default logger, on stdout, and those layers log outside the command. The library adds no runner for them, which would compete with Effect's: a CLI whose stdout feeds scripts provides `Logger.LogToStderr`, turns off `runMain`'s report and reports on stderr itself, as ActionCli.md shows.
- A command's services and caller are provided on the command, with `Command.provide`, `Command.provideSync` or `Command.provideEffect`, where the docs and examples provided them around the run since cd08952: around `Command.run`, a layer is built before the arguments are parsed, so `--help` and a mistyped flag opened the database, and a missing identity config failed instead of showing help. On the command, a provision wraps only its handler, which help and a parse error never reach; the handler decodes the input, so input the schema refuses is refused after the provisions are built. A remote command's `HttpClient` is configured on the remote command or aggregate the same way, where cbb7113's example updated it for the whole program: that rewrote every request the program made, a login request's absolute URL too, and put the API's credentials on each. One case is Effect's own: `make`'s aggregate run alone runs its provisions, then its handler shows help, so a bare `users` still builds them, and fails instead of showing help if one fails.
- `Action.client` calls implementations in process with `ActionHttp.client`'s shape, one method per action taking its input directly, so moving between an in-process and a remote caller changes the line acquiring it. A call fails with what an HTTP client decodes as values, the action's errors and the built-in ones, and with nothing of a transport: input that does not pass is `InvalidInput`, where an HTTP client's own encoding fails with a `SchemaError` before sending, and a binding's errors are its middleware's, which no handler or hook fails with. Input, success and failure each pass through their JSON codec, encoded then decoded, as a wire carries them, a failure through every error its action declares, the built-in ones included, so the handler receives, and the caller gets, what a remote call's would: an undeclared field dropped, a class instance built anew, a decoding transformation such as a trim applied. A success or a failure that does not encode or decode, an error the action does not declare included, is a defect, as it is an empty 500 over HTTP. A success that does not is a defect on the CLI too, which prints a failure no schema encodes by name, since a builder's or the transport's is one; a call's failure never is, since a client builds when it is acquired and has no transport. A failure is mapped within its cause, which keeps the span it failed in, and takes the stack of the error it replaces: failed anew, its trace would start at the codec. Checking the type side alone (`Schema.toType`) would hand the handler the caller's own values, untrimmed, and pass a success whose encoding fails, and passing a failure on as it is would keep a trimmed field untrimmed and type an undeclared error, so a test through the client would pass where every surface differs or fails. Each method owes per call what the handler and the hook read, provided around the call, and the acquisition owes only the builders' startup services and a `Scope`, failing as they fail, as `Layer.build` does. Captured at acquisition, the caller of a client acquired in a builder or a layer would be a startup identity, which the invariants forbid, and one client would serve one caller. A call reads its caller's context alone. HTTP and `Toolkit.handle` lay their build context beneath a request's (3a4275c); a client does not lay the acquisition's beneath a call's, where a caller provided around the acquisition would reach every call its types say owes one, and a span around the acquisition would parent every call made outside one. Acquisition builds into the memo map of the layer graph around it, `Layer.CurrentMemoMap`, as `HttpRouter` builds a middleware's dependencies, or into a map of its own under none, so a builder acquiring a client shares each builder's one run with the surfaces of its graph, whichever builds first; a fork, as `Layer.build` makes, runs it twice when the acquiring builder builds first. A local CLI command still builds per invocation (79e02ce): an invocation is one call, where a client serves many. Under `Action.share`, a client calls the share's actions with its source's handlers behind the share's hook, as every surface serves a share. It lives in `Action`, beside the implementations it calls, and imports no transport: the call rule every client shares, `Call` and `inputOf`, moved out of the HTTP client's module, and `tests/browser.test.ts` checks `Action`'s imports.
- An implementation's own behavior is tested in process, with `Action.client`, and a surface's under `Testing.layer`. This reverses b0dc80a's choice to test handlers behind their hook through a surface alone, `Testing.layer` as one caller and a test binding of its own for an action no binding holds: a test had one caller per layer, a tool-only action needed a binding, and one implemented beside others an `Action.share` too. `Testing.layer` keeps what only the wire shows: authentication, statuses, codecs as sent, MCP results. A command built with `Command.make` that calls a client is the host's own: the hook and every check run, but not ActionCli's output rules, so a failure it leaves as it is reaches `runMain` as the action's error, printed on stdout with a stack and without its fields. The docs prefer a derived command wherever `name`, `positional` and `render` express the syntax, and otherwise state the difference and map the failure to Effect CLI's `CliError.UserError`, rather than add a helper giving native commands ActionCli's failures: a second way to build what `ActionCli.command` builds, for commands whose output is the host's anyway.
- The binding decides what `ActionHttp.layer` serves: its actions among the implementations given, matched by identity. An implementation's other actions get no route, and their names are not read. This reverses c971b1a, which carried the group era's refusal (33158a4, `Implementation of group "x" is not served by this adapter`) over to flat lists as `Action "x" is not in this HTTP binding`, when `implement([a, b])` still made one implementation per action. 4431b09 made it one implementation of all its actions and kept the refusal; 1791581 and `share` (9a0d0a2) worked around it. An agent-only tool beside HTTP actions took an implementation of its own, its builder preamble and hook repeated, or a third copy of the HTTP list at every layer call, where a missed action compiled and its client call answered 404. An implementation holding none of the binding's actions is still refused, in the types and at runtime, as the wrong implementation or the wrong binding; the message marks a bound name `(another contract)`, as a second copy of the contracts module makes one. A look-alike beside bound actions is not refused by name: that would read names HTTP does not serve, and refuse an HTTP route and an MCP tool of one name from different contracts. The type check picks its entry by a key distributed over the binding and the implementations, so a helper whose binding or implementations are its own type parameters still compiles, the key read through their constraint: an erased binding serves, and an erased implementation owes `unknown`. One listing its type parameter beside another implementation, which 0.8.0's `Http.layer([app, double])` allowed, or making a binding or a share of generic actions, does not, as a listed type parameter does not on MCP: the key stays deferred, and indexed by its constraint, both entries, the parameter demands the refusal's property. Any deferred conditional key has that constraint, so the docs give the helper forms that compile: the implementations spread from one type parameter, the binding as one, a share passed in. Request requirements narrow per implementation, to its hook and the handlers it serves; build requirements stay whole, as the builder is built whole. The cost: binding an action serves it in every layer whose implementations hold it, under that layer's middleware, so a public layer takes only implementations of public actions, and one implementation holding both is split with a share per layer. No type tells a public layer from a protected one, since authentication is middleware provided after `layer` returns; the identity a handler or hook reads is the check the types give. A marker service that authentication provides and `layer` requires was rejected: every custom middleware and test would have to provide it too.
- `ActionHttp.make`'s `security` documents what the authentication around the routes reads, and `public` the actions served without it. `make` adds native security middleware, an `HttpApiMiddleware.Service` with `security` keyed per binding, to every other endpoint: the one way `OpenApi.fromApi` writes both `components.securitySchemes` and each operation's requirement, and it survives `addHttpApi`, Swagger and Scalar. It is not `requiredForClient`, so clients are unchanged. `layer` rebuilds its endpoints from the actions at the binding's paths without it, rather than satisfying it with a pass-through, so the documentation never runs on a served route and authentication stays router middleware, the only enforcement. Rejected: an `OpenApi.Transform` recipe, which is untyped, is overridden by each operation's `security: []` when set at the top level only, and throws once `addHttpApi` moves it onto a group; metadata from `Authentication.make`, which the contract-level `Http.api` cannot see without a library document route, reversing b22618f; and the native `Http.api.middleware(Bearer)`, which marks public actions protected too. The first README (bfc6690) named that native middleware as the way to document a scheme, and 10a0171 dropped the line in a cleanup. Limits: `public` and the layers state one split twice and can drift, the default documenting every action as protected; Effect has no OAuth or OpenID Connect scheme, so an OAuth resource is documented as a bearer; and serving `Http.api` with the native `HttpApiBuilder` fails on the missing middleware.
- Surfaces write their return types out, as `ActionMcp.layerHttp` does: `ActionHttp.layer`, `ActionToolkit.make`, `ActionCli.command` and `make`, and `share`'s request map. A hover then shows what a layer or command still needs and fails with, `Layer<never, never, … | Request<"Requires", CurrentActor> | Users>`, where a private alias named the implementations (`ActionHttp.layer(Http, [userActions, double])`'s hover: about 600 characters, now about 145). A remote command's failure is written out as its client method's, the action's errors, the binding's, the built-in ones and the transport's, where the client's private `MethodError` hid them. `layer`'s `Apps` drops the redundant `Served &`. `ActionCli.make` and `command` list the binding overload, then the implementations overload, then a catch-all taking either: TypeScript 7 reports a call matching no overload by the last one's error alone, and the catch-all's names every option mistake in both forms, such as a misspelled `commands` key or a positional argument that is not a field, where a last precise overload reported a mistake in the other form as its target not being assignable. It is reached only when both precise overloads fail, so every call they type is typed as before, a helper generic in the binding or the implementations included. Its cost: a target chosen by a condition between a binding and implementations, which both precise overloads refuse, compiles there, owing `unknown`, and `runMain` refuses it instead. `Parameters<typeof ActionCli.make>` reads the catch-all, which a spec pins. A single conditional signature would name every cause too, but broke a helper generic in the binding.
- A message for input that does not decode never carries a value of the input: every surface formats Effect's schema issues with `reportInput` off, its default, which keeps values out of each issue, so the message names paths and expectations. A path names the keys it passes through, as Effect's issues keep them, a record's included, so a record keyed by an email names the email. Checked on HTTP, MCP, the Toolkit, the CLI and `Action.client` with a `Schema.Redacted` field and plain strings; a test pins each surface, and fails with `reportInput: true` on HTTP's or the CLI's decoding, or on `Action.client`'s codec. No option turns it on. Effect CLI's own parser, which reads a flag before the schema decodes it, names a rejected choice, an unknown flag or an unexpected argument as typed, to whoever typed it; keeping it out would take the parser's messages over, or no choice flags. A custom message is the schema's author's, sent as written. ## Release

The package publishes to the `latest` tag. The `effect` peer accepts any Effect 4.0 release
candidate from `4.0.0-rc.118` on (the peer's lower bound); the package is built and tested
against the release candidate in `devDependencies`. When
adopting a newer release candidate, bump `devDependencies`, re-run the full check, and raise the
peer's lower bound only if the package starts to depend on the newer release.

To release: set `version` in `package.json`, add its section to [CHANGELOG.md](CHANGELOG.md)
(every breaking change and how a consumer migrates), commit as `Prepare <version>`, tag
`v<version>`, and push the commit and tag. The tag runs `.github/workflows/npm.yml`, which checks that the tag
matches `version`, repeats the CI checks, and publishes. It authenticates as the package's npm
trusted publisher (this repository and that workflow file, set under the package's npm
settings), so there is no registry token, and npm attaches provenance.
`prepublishOnly` builds; `files` ships `dist` and `docs`. The skill is not in the tarball:
`npx skills add` reads it from GitHub, and agents reading node_modules get `docs/` directly.

## Lint policy

`vite.config.ts` is the source of truth for rule severities; this section explains the
decisions behind it. The vendored plugin's provenance and local corrections are in
[`tools/oxlint/anti-slop/UPSTREAM.md`](tools/oxlint/anti-slop/UPSTREAM.md).

Strict rules are the goal, and lint passes because the code is correct, not because it was
rewritten to satisfy a pattern matcher. A passing lint run is not evidence of type safety by
itself: type safety comes from the compiler flags below and the type-aware `typescript/no-unsafe-*`
rules.

### What is checked

Every owned file: `src`, `tests`, `examples`, `scripts` (including the package-consumer fixture
and `scripts/test-package.mjs`, checked as JavaScript with `allowJs`/`checkJs` and owner-derived
JSDoc types), the plugin regression tests in `tools/oxlint/tests`, and `vite.config.ts`. Lint runs
type-aware with type checking, so `vp check` is one command for format, lint, and compiler
diagnostics.

Excluded: build output (`dist`), agent caches (`.claude`, `.codex`, …), and the vendored plugin
sources under `tools/oxlint/anti-slop`, which follow upstream's own style and are covered by the
regression tests beside them. Nothing owned is excluded to hide findings.

Compiler flags required by policy and set in `tsconfig.json`: `strict`,
`exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`. The assembled package consumer
(`scripts/test-package.mjs`) compiles with the same three flags, so a child configuration does
not weaken them.

### Refactor before making an exception

For each finding:

1. Identify the invariant and who owns it. Does the diagnostic expose a missing boundary, erased
   type information, duplicate validation, or an unnecessary abstraction?
2. Prefer the refactor that removes the cause, even across owned APIs. Update callers and tests
   directly; do not add compatibility wrappers to keep an old shape.
3. Preserve concrete safety: third-party contracts, malformed external input, and runtime
   compatibility survive API changes.
4. Distinguish a rule defect from a legitimate exception. A defect is corrected in the vendored
   rule with a regression test and an `UPSTREAM.md` entry. A legitimate case intentionally caught
   by a broad rule gets the smallest justified exception.
5. Exceptions are line-level (`oxlint-disable-next-line <rule> -- <reason>`) or a tightly bounded
   disable/enable pair. The reason names the boundary and what the operation still guarantees.
   An unused directive is an error (`reportUnusedDisableDirectives: "deny"`).

Never launder a finding: renaming a parameter, dropping an annotation so inference yields `any`,
casting, moving a `typeof` into a one-use helper, or moving code to an unchecked file leaves the
code exactly as unsafe.

### Rule families

- **Unknown and broad inputs** (`no-unknown-parameters`, `no-unknown-returns`,
  `no-unknown-type-aliases`, `no-object-parameters`, `no-unsafe-dictionary-type`): decode at the
  I/O boundary and pass owner contracts inward. There is no name-based exemption; a parameter named
  `cause` is as unknown as any other, and thrown-value boundaries use an explained directive.
- **Evidence loss** (`no-known-value-widening`, `no-widen-then-assert`,
  `no-chained-type-assertions`, `require-safety-comment-for-type-assertion`,
  `typescript/no-unsafe-type-assertion`): keep inference or validate with `satisfies`. A SAFETY
  comment is necessary, not sufficient; the type-aware assertion rule needs its own explained
  directive when an assertion is a genuine erasure boundary.
- **`any` escape routes** (`typescript/no-unsafe-assignment`, `-argument`, `-call`,
  `-member-access`, `-return`): untyped JSON, SDK generics, callback registries. Type the value at
  its source, for example by importing `package.json` as a typed JSON module instead of parsing it.
- **Runtime probing** (`no-runtime-typeof` with `allowInTypeGuards`): a genuine type predicate may
  probe its subject; discriminating an already typed union takes a narrow explained exception.
- **Quadratic copies** (`no-reduce-accumulator-copy`, `oxc/no-accumulating-spread`): growing copies
  in a loop; fixed-size snapshots may justify an exception.
- **Reflection** (`no-reflect-apply`, `no-reflect-get`): prefer typed access; keep a concrete
  exception only where receiver or getter semantics matter.
- **Module mocking** (`no-module-mocking`): replace dependencies through real seams. The rule
  recognizes `vi` from `vite-plus/test`, this repository's test import, as well as `vitest`.
- **Compile-failure fixtures** (`tests/types.spec.ts`): an expression under `@ts-expect-error`
  yields an error type, which the `no-unsafe-*` rules see as `any`. Those lines carry a directive
  stating that nothing runs; the fixture's purpose is the compile failure itself.

Off, with reasons recorded beside the setting in `vite.config.ts`:

- `anti-slop/no-array-filter-map`: both forms are linear; rewrites change callback order and
  sparse-array semantics without establishing a performance gain.
- `anti-slop/no-conditional-empty-object-spread`: conditional spread preserves omission semantics
  without mutable builders.
- `anti-slop/no-shape-in-symbol-names`: a substring cannot establish domain ownership; naming is
  reviewed by people.

### Verification

- `tools/oxlint/tests/rules.test.ts` runs the corrected rules through Oxlint's `RuleTester`,
  with an accepted and a still-rejected case for each correction.
- `tools/oxlint/tests/configuration.test.ts` runs `vp lint` on fixtures inside the repository, so
  the probes go through the registered plugin and the effective configuration: unknown parameters
  named `cause`, module mocking via `vite-plus/test`, `typeof` inside and outside predicates, a
  justified `no-unknown-parameters` directive and its unused counterpart, maintained JavaScript,
  and the three disabled rules.

### History

Historical measurement, not a backlog: when the baseline was adopted (2026-09-19) the repository
had zero findings under the previous configuration. Enabling the `typescript/no-unsafe-*` rules and
widening coverage to the scripts surfaced 60 findings, all resolved by refactor or by the
explained directives listed above. Two rule-behavior gaps (`cause` exemption, unrecognized
`vite-plus/test` import) and two false positives in `no-known-value-widening` (destructured
bindings inheriting the initializer's evidence, finite mapped keys classified as open
dictionaries) were corrected in the vendored rules.
