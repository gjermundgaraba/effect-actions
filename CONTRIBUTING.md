# Contributing

For people and agents changing the library. Consumers read [docs/](docs/README.md) instead.

## Setup

Requires Node.js `^22.18.0 || ^24.11.0 || >=26.0.0` (`devEngines` in `package.json`; CI tests 22, 24 and 26) and [Vite+](https://viteplus.dev). Run `vp install`, then see
[AGENTS.md](AGENTS.md) for the commands, the repository map, and the validation rules.

Vocabulary: [docs/CONTEXT.md](docs/CONTEXT.md). Use its terms in code comments, docs, and tests.

## Documentation rules

- `README.md` sells the library to humans: the pitch, one showcase snippet, why, install, links. No reference material.
- `docs/` is for coding agents. Each public-module reference card has the same sections: **API**, **Canonical**, **Rules**, **Failure modes**. State what holds and what breaks, without tutorials or narrative. Routing, setup, vocabulary, and shared guarantees use the structure their role needs.
- `docs/README.md` is the routing table and doubles as the skill body. One line per page saying when to read it.
- A change to public behavior changes the matching `docs/` page in the same commit. Then run `vp run docs:sync`; `tests/skill.test.ts` fails if the generated skill is stale.
- API sections inventory exports and options; do not hand-copy complex generic declarations. Exported TypeScript declarations are the exact signature reference.
- A snippet fenced as ` ```ts example=<file> ` stays byte-identical to that file in `examples/`, which `tests/docs.test.ts` checks, so it stays type-checked; the first snippet of every Canonical section is one. Edit the example, then paste. Compile-only tests assert public API behavior directly, without maintaining a second type definition.
- `docs/CONTEXT.md` defines terms. Add a term there before using it in docs.
- A rule that holds on every surface lives once, in `docs/guarantees.md`. A module card states what is its own and links there; a restated rule drifts.
- Docs describe behavior, not the code: no page names a `src/` path, and `tests/docs.test.ts` checks it. Implementation rationale belongs in code comments or below.
- Tests assert this library's behavior. Effect's or MCP's own wording is matched by its stable fragment (`toContain('at ["value"]')`), never in full, unless a doc quotes it. A test of Effect's own behavior stays only when a doc promises that behavior: the 415, CORS preflight, the generic MCP defect text.
- Every file in `examples/` is listed in `examples/README.md`, which `tests/docs.test.ts` checks; `docs/README.md` links there rather than keeping a list of its own.

## Tests

- Tests import Vitest through `@effect/vitest`, which re-exports it. The pnpm catalog pins `vitest` to the version Vite+ depends on (`vp toolchain vitest`), and an override holds every package to it, Vite+ included, so one Vitest is installed.
- A test running an Effect is `it.effect`, which provides a scope, a `TestClock` and a `TestConsole`: it serves its routes with `Testing.layer(routes)` in its scope, sending a raw request with `send`, and what it logs is captured. A command's lines are read from a console of its own run (`logged`, `printed`), so a test running several reads each one's. A codec that completes later awaits a resolved promise, `Effect.promise(() => Promise.resolve())`, which no `TestClock` holds, where `Effect.yieldNow` would still complete synchronously; a test whose handler waits on real time is `it.live`.
- A test that runs no Effect stays `async`, such as one sending raw requests to a web handler, which `serve` releases when the test finishes. So does a test of an Effect run under no layer, of a context given per request (`serveWithContext`), of `Testing.layer(handler)` run from a Promise test, as a downstream harness runs it, and one pinning a missing requirement with `@ts-expect-error` on `Effect.runPromise`, which `it.effect` would report at the test instead. An `it.effect` test takes `serve`'s handler only to wrap it, recording what a client sends, or to answer a program that provides its own client.
- Each test provides the layers whose state or builds it reads, such as `Users.layerMemory`, rather than sharing one through `it.layer`.
- Type pins live in `*.spec.ts` and use `expectTypeOf`; a compile failure is an expression under `@ts-expect-error`, which a runtime test may also put on a call it makes as plain JavaScript would.

## Design notes

Each note is titled, and cited by its title. It states the decision, why, what it costs, and the alternative it rejected; a reversal names the decision it reverses, by commit where one recorded it. History beyond that belongs in commit messages.

- **Strict HTTP input.** HTTP input is strict through `HttpApi.PayloadParseOptions` alone. A strict `ParseOptions` would also govern error encoding, where it could turn a declared error into an empty 500. Only `layer`'s own API carries it: a client encodes with Effect's default, dropping a field the input does not declare, as TypeScript lets a wider value through. This reverses 0.8.0, whose typed clients failed with `SchemaError` before sending such a call, one the compiler had accepted. An action without input is `Schema.Record(Schema.String, Schema.Never)`: `Schema.Struct({})` accepts any value but `null`, and has no object root for MCP.
- **Schema failures.** Schema failures take no policy. Input that does not decode is the built-in `InvalidInput` over HTTP, from the CLI and from `Action.client`, and the native invalid-arguments answer over MCP and the Toolkit, so no application declares an error for it; a success that does not encode is a defect, an empty 500 over HTTP. This reverses 0.6.0's two-answer `schemaError` policy, `invalid` and `internal`: such a success means the handler broke its contract after it ran, so any write it made has happened, which a declared error would misreport, and defects, crashes and proxies send a 5xx without a declared body anyway. `InvalidInput` also lists the failure's `issues`, each `{ path, message }`, from Effect's Standard Schema formatter over the same `SchemaIssue` its `message` describes, and a handler may name its own: an application kept a second error for bad input, with its own `issues`, only because the built-in one carried a string, so a client matched two tags for one fault. The field is optional, so a refusal written with a message alone stays valid; MCP and the Toolkit keep their native answers, which have no field for it.
- **MCP over HTTP.** MCP over HTTP serves 2026-07-28 only. The stateful revisions work over Effect's HTTP transport, and request identity stays per request, but each `initialize` registers a session that Effect's runtime never deletes, with no expiry and no `DELETE` termination, and any caller holding the session id may use it.
- **MCP over stdio.** MCP stdio keeps the stateful revisions 2025-11-25 and 2025-06-18 until hosts speak 2026-07-28. Measured on 2026-09-29 against Claude Code 2.1.284 and Codex 0.159.0. Both open stdio with `initialize` (2025-11-25 and 2025-06-18), so neither connects to a stdio server that serves 2026-07-28 only. Codex also opens HTTP with `initialize`, so it cannot connect to `layerHttp` at all. This reverses keeping every stateful revision back to 2024-11-05: no measured host asks for 2025-03-26 or 2024-11-05, and Effect's adapters for them list an input's root alone, open, with a `$ref` resolving nowhere for an identified or recursive field, nor tool hints on 2024-11-05. A host asking for one is offered 2025-11-25, as MCP negotiates, and disconnects if it cannot speak it.
- **Successes unwrapped.** A success is sent as it is, never wrapped. 2026-07-28 carries any encoded success as `structuredContent`, a bare number, string, array or `null` included, with its JSON as text, and Claude Code accepts all of them. On the earlier revisions Effect's adapters decide, not our code: 2025-11-25 and 2025-06-18 structure, and list an `outputSchema` for, only an object; a success they do not structure is text alone, a string as itself. This reverses the earlier decision to keep the `{ value }` envelope while stdio serves the 2025 revisions: 0.8.0 already shipped bare successes, and a downstream app documents them, so the envelope would wrap them again now and unwrap them again when those revisions go. The Python SDK rejects a `null` `structuredContent` (python-sdk#3345); that is the SDK's bug.
- **Text field.** A text field is the contract's `text` hint, `hints: { text: "markdown" }`, as 0.8.0's `mcp.text` was. This reverses the unreleased 0.10.0's `tools` option of the MCP server, chosen because a contract held no surface's options: which field holds the document is a fact of the success that every endpoint and every client of the action must agree on, so on the server every `Testing.mcpClient` repeated it, and a mismatch was a failure the docs had to describe; `hints` already carries what tools show. Lost: one contract sent as text by one endpoint and as structured content by another, which now takes two contracts. Its tool sends text alone, as a downstream app's earlier server sent each page of a fetched document: a success whose field holds a string is two text blocks, that string raw, then the JSON of the rest, and any other success the JSON of the whole, with no `structuredContent`, and the tool lists no `outputSchema`. This reverses 0.8.0's and the unreleased 0.10.0's rest as structured content: a host that prefers structured content then showed the model the rest without the field, the page itself, and the rest was sent twice, which a consumer bounding each result's encoded size, 8 KiB a page, pays for on every page. Lost: a typed `structuredContent` for a program reading the result as data, which reads the JSON of the second block instead. Native `McpServer.registerToolkit` builds every listing and result with the whole success as structured content, so `ActionMcp` registers the toolkit on a copy of the registry whose `addTool` lists the tool without its `outputSchema` and wraps the tool's handler. Every other result is the native one, so decoding, failures and defects stay native, and each revision's adapter sends the text as it sends any, so every revision sends the same blocks. A field that is not a top-level property of the success's listed schema is refused when the server is made, naming every such action beside any input refusal, rather than name a field no success holds. `make`'s types accept only a top-level string field of a struct success, where 0.8.0 let a union's through to that failure; an erased success, or a hint typed only as `string`, may name any field. `Testing.mcpClient` reads the hint and such a tool's success from its text blocks. A native option shaping a tool's result would delete the copy.
- **Request values win.** A request's own value wins over a startup value under the same tag, on every surface. `HttpApiBuilder.group` and `McpServer.registerToolkit` apply the context they are built in on top of each request's. So `ActionHttp.layer` builds its group in an empty context, where the group finds only its `HttpApiMiddleware`, and a route middleware of each layer runs its routes over `Context.merge(startup, request)`, without the layer's `Scope`. `ActionMcp` registers its toolkit with only the registry and the tool handlers; `Toolkit.handle` already puts each handler's build context beneath the call. Both rely on those functions reading nothing else from their build context: a service they start to read fails the layer build, but a reference would silently take its default. A protected action's identity is the exception since "Contract identity": only its descriptor's provider gives it, and the types refuse any other, a startup value or `HttpRouter.provideRequest` included; over MCP it is promoted at tool entry, never in local calls. Re-applying the identity inside the shared dispatch was rejected: a Toolkit call a handler makes under a narrower identity would run as the signed-in caller. The merge wraps the whole route rather than the handler call, so `HttpApi`'s own error reporting runs once, in the merged context.
- **JSON-typed routes.** `ActionHttp` routes take only JSON-typed requests. The same route middleware answers a request without a content type with 415 before `HttpApi`'s default reads it as JSON, so every POST a page can send without a CORS preflight (no type, `text/plain`, the form types) is a 415, and cookie credentials cannot drive a cross-site write. Each endpoint pins its payload to JSON with `HttpApiSchema.asJson()`: an input annotated with another encoding made `HttpApi` take that type, a form body answered 200, where no other surface reads the annotation. Refusing such an input at `make` was rejected: a contract every other surface serves would be one HTTP could not bind, for an annotation HTTP alone reads. As on the MCP endpoint, the check runs after the middleware around the layer, and on a protected route after authentication, so a request without a credential is a 401 before a 415 or a 400: authentication reads no body.
- **Authentication descriptor and provider.** `Authentication.make(name, identity, { security })` is a browser-safe declaration a binding and an MCP endpoint name, of one native scheme, and `Authentication.layer(descriptor, verify, { protectedResource })` its server-only provider, built once per layer graph, whose verifier, given as it is or built by an Effect, as a handler is, receives the credential the native scheme decoded. The descriptor's public fields are `name`, `service` and `security`; its wiring is `~provider`, `~middleware` and `~verified`, and the security middleware's identifier is its own, not the provider's: when both shared one, a host listing the descriptor's middleware in a layer's `middleware` compiled against `layer(Login, ...)` and failed to build, and the provider type had to carry Effect's middleware marker. This reverses "Authentication as middleware", where `make` returned Effect's `HttpRouter.Middleware`, composed with `.combine`, and provided around layers: what it covered depended on where the host provided it ("Contract identity"), a public and a protected action took separate layers, and one layer could not refuse before decoding for some of its routes alone. Per-endpoint authentication, the descriptor's native security middleware on each protected endpoint, lets one layer mix public and protected actions and authenticate each protected request before its body is read. Lost: a route of the host's own under the same middleware; it reads `bearerToken`, calls the same verify function and answers with `refusal`. `.combine` is gone with it. Middleware feeding the verifier, such as a tenant resolved per request, stays native router middleware, provided in a later `Layer.provide` than the authentication; middleware reading the identity is `ActionHttp.layer`'s `middleware`, native `HttpApiMiddleware` run inside authentication and outside decoding, the first listed innermost, as native chaining is, whose requirements fold through native `ApplyServices`, which discharges the identity only where every action the layer serves is protected, and which may fail only with the binding's `errors` and need no client, since clients decode only what the binding declares: a failure callers see after decoding, on every surface, is a check. The first version refused every middleware error; that blocked a limit keyed by the caller that also counts input that does not decode, which neither a check, after decoding, nor router middleware, before authentication, can be, while an error the binding declares already reaches every client. The option sits on the layer, not the binding, which browser clients import and whose client API never declared it. Not fixed, documented: `Layer.provide([authenticate, tenant.layer])` as one array leaves the verifier's per-request service owed, since an array's members provide to the routes and not to one another; the docs show sequential provides. Rejected: carrying the verifier's per-request `R` on the provider's type so the routes owe it instead, which retires the trap: the routes' layer is built before the verifier exists, so it could owe `R` only if the browser-safe descriptor declared it, `Authentication.make(..., { requires: Tenant })`, a new concept to save one wiring order. Not built: identity-reading middleware on MCP, which `.combine` covered; an `Action.Check` observing the call's `Exit`, or a post-verification request scope shared by both remote adapters, were proposed, and wait for a concrete need, as the only consumer, a caller log, sets an HTTP header. Routes of the host's own, such as a WebSocket upgrade, use native middleware reading `bearerToken` and answering with `refusal`.
- **Refusals outside the router.** `Authentication.refusal` renders a refusal as authentication answers it, from the same functions: one implementation each of the status and JSON, `no-store` and the 401's challenge, the challenge's quoting, the rule for a presented bearer token, RFC 6750's `error_description` and the metadata URL. `make` does not answer through `refusal`: its pre-response handler sets `no-store` and the challenge on every response of its routes, a refusal's among them, so its failure path answers the status and JSON alone, and `refusal` applies that same header step itself, once. Rendering in both places settled each of `make`'s refusals twice. This partly restores 0.9.0's `protectedResource().challenge()`, which 0.10.0 removed with `protectedResource` on the grounds that `make` writes every challenge. That holds for routes only: a caller the router never routes, such as a Node `upgrade` handler admitting a socket, authenticates its own header and still owes the same answer. The one downstream SDK with such a caller rebuilt the challenge by hand, and its copy had drifted on four rules: it escaped nothing, counted `Bearer a b` as a presented token, always sent `error_description`, and named the metadata URL without the resource's path. It returns the whole response rather than the challenge string 0.9.0 gave, since a status and body chosen apart from the challenge is where a copy drifts, and takes the `Authorization` header rather than a flag, so the presented-token rule stays the library's. It is a plain function, not middleware state: it derives the one challenge it answers with from the options each call, where `make` writes its two once, so a caller passes the resource it gave `layer`, and nothing ties the two but that. It takes the descriptor too, `authentication`, so a host route under a scheme other than Bearer answers as that scheme's routes do, not with Bearer's challenge. `bearerTokenOf` is exported beside it for the same caller: it holds a header and no request, so `bearerToken` cannot read it, and the canonical example's own reading had already drifted from the library's, admitting a header with no scheme and refusing a trailing space. `bearerToken` and the presented-token rule read through it, so the header has one parser. It reads the header as Effect's `HttpApiSecurity.bearer` decodes a request's, the reading a Bearer descriptor's verifier receives, which a test pins against `securityDecode`: the whitespace around the value stripped, as HTTP parsers do before a route reads it, then the scheme, its spaces, and the rest of the header. This reverses the rule above that `Bearer a b` is no presented token: the verifier received `a b` while the challenge said nothing was presented, two parsers of one header, and RFC 6750 §3.1 counts a malformed token as `invalid_token`.
- **Built protected resource.** `Authentication.layer`'s `protectedResource`, `Authentication.make`'s before the descriptor and provider split, is a plain resource or an Effect that builds one, told apart by `Effect.isEffect`, as a built authorizer is: it runs where the middleware's layer is built, before `build`, once per layer graph, its failures and services the layer's, its scope the layer's own, and may succeed with none. A downstream SDK learns its resource from a service at startup, so it wrapped `make(...).layer` in `Layer.unwrap`: that leaves a plain `Layer`, and its consumers could no longer `.combine` the authentication with middleware of their own. The plain form is unchanged: its challenges are written and its `scopesRequired` checked where `make` is called, so a misconfigured literal still throws at module load; a built one's are when the layer builds, the check a defect there, never per request. Not taken: `build` returning the resource beside the authentication, which every caller would write for the one that builds its resource.
- **Request body size.** Request body size is host configuration, not a library option: the host provides `HttpServerRequest.MaxBodySize` to `HttpRouter.serve`'s layer. It is Effect's server-wide setting and covers every route, the host's own included; an option per surface would duplicate it for only some of them. Node's server drops an over-limit request without a response. A web handler ignores the setting, so its platform limits bodies.
- **TypeScript 7.** TypeScript 7 or newer only. The package is type-checked on the pinned TypeScript 7 alone, and adds no signature workaround for an older compiler's inference.
- **Handler requirements.** `implement` infers what each handler owes into one map, `R`, reverse-mapped from a list's record key by key (`Several`), and `RS` for one action's handler; plain handlers and builders take the same path. So a handler is typed from its contract however it is written, unless its builder reaches `implement` through `.pipe(...)` or an overloaded wrapper such as `Effect.withSpan`: TypeScript gives the Effect before `.pipe` no contextual type, and types an overloaded call's arguments from its first overload. The record was once inferred whole, as `H`, and checked afterwards (`Exact`): a generic handler, such as one `Effect.fn` makes, then had no contextual type and took an `any` input, where 0.8.0's `group.implement` had typed it. A list takes no single handler, which `NoHandler<R>` states. It must stay a named alias: while a builder's inner generic call, such as `Effect.gen`, is inferred, an alias's type arguments keep TypeScript's mark that they are not yet inferred, where `never`, or the same object type written inline, becomes a real candidate and the builder's record loses its contextual types (`examples/handlers.ts` then fails with TS7031, as the specs do). One action's handler and a built authorizer are the reverse, and must stay written out rather than `Handler<T, RS>` and `Authorize<A, RB>`: an alias carrying `RS` or `RB` before they are inferred bears that mark as a whole, so an `Effect.fn(...)` that a builder, or an Effect building the authorizer, returns would infer nothing from it and take an `any` input or action (the specs' `@ts-expect-error` pins then go unused). One action's `R` is constrained to `never`, so a record keyed by its name is refused, and a list's record must have a key for every action. Reverse-mapped inference costs instantiations superlinear in a record's size: measured on TypeScript 7.0.2, one `implement` of 60 actions adds 59k instantiations (25k before), of 150 adds 255k (62k), of 300 adds 869k (124k) and 0.2 s. A record's handler may still be inferred to owe `unknown`: its return type is typed from its own entry of `R`, not yet inferred, which TypeScript reads as the constraint's `unknown`, and a generic call there takes it for any type parameter no argument gives. `Effect.catchTag`'s data-first overload has one, the `orElse` handler's services, defaulted for the argument left out; `catch`, `map`, `orDie`, `flatMap`, `mapError` and `Effect.gen` have none, nor has one action's handler, whose `RS` is a parameter of its own. `unknown` then reaches a surface's requirements as `Request<"Requires", unknown>`, an error where the server is launched that names no handler, and the remedy is documentation, the Action card's failure mode: write that Effect with `.pipe(...)`. Neither the arguments nor the result can say more. A rest parameter typed from `R`, empty unless an entry is `unknown`, made TypeScript infer `unknown` for every record, 75 errors across the tests and specs, and `Several` cannot test its own entry without losing the reverse mapping that types each handler. A label in the result type, an object type naming the handler where its entry is `unknown`, was tried and removed: `unknown extends R` stays unresolved for a generic `R`, so a helper taking a handler and the layer that provides it could no longer discharge its requirements.
- **Deferred build channels.** `implement`'s build channels are `Deferred<T>`, `[T][T extends unknown ? 0 : never]`, rather than `NoInfer<T>`. Either keeps an implementation written inside a surface's arguments from inferring them from the surface's parameter, where they would be `unknown`. `NoInfer<A | B>` also survives into a layer's requirements, where providing `A` and `B` in two `Layer.provide` calls leaves it owed, and shows in every hover; `Deferred` reads as `A | B` once inferred.
- **Contract identity.** A contract states who may call it, `auth: "public"` or the identity service a caller must have, required on every `Action.make`, and every surface enforces it whatever the handler reads: a remote surface authenticates a protected action through the descriptor its binding or endpoint names before decoding, and a local one owes the identity per call in its types and fails a call without it with `Unauthenticated`. This reverses "Required hook" (since 09051f7, made required in the unreleased 0.10.0), where every `implement` stated a hook, `Action.allowAll` for a public one, and authentication was router middleware the host provided around layers: whether an action was authenticated depended on which layer served it, so a protected action given to a public layer answered anyone, an admin write whose handler read no identity compiled with no authentication around it, and a public action beside protected ones took an `Action.share` per layer. Now the contract decides, once, for every surface, and `{ authorize }` is required exactly where the target holds a protected action and refused, a compile error, where it holds none, since nothing would run it; `implement` throws for a missing one from plain JavaScript, as `make` throws for a missing `auth`. `Action.allowAll` now means every authenticated caller. One identity per action and per remote surface: tenants and other context stay ordinary request services, and several identities on one surface are not supported. Identity declarations are `Context.Service`s, so contracts importing them stay browser-safe; that holds for the examples, not for every application module, which no type can check. Rejected: the contract's `auth` naming the authentication descriptor itself, `auth: Login`, which would drop the `authentication` options of bindings and endpoints and their consistency types: a descriptor carries `HttpApiSecurity` from `effect/http-api`, and contracts never import transport code, so every Toolkit-only or CLI-only consumer would carry HTTP security on each contract.
- **Built authorization.** An authorizer may be built by an Effect, as handlers are, and each implementation keeps it in a memoized layer of its own beside its handlers'. `Effect.isEffect` tells the two forms apart, as it tells a builder from a handler, so an `Effect.fn` authorizer stays plain, and a service whose value is the authorizer is an Effect building it once per layer graph for every implementation it guards. A built authorizer's own state is per implementation; state shared across implementations belongs in a service. The type keeps its builder's failures and services apart from the handlers' (`~authorizeBuildError`, `~authorizeBuildContext`). This keeps "Built hooks" but drops what it served a share for, replacing the hook of some actions while keeping their handlers: `Action.share` is removed, so another authorizer over the same handlers takes another `implement` of the same builder Effect, whose builder then runs once per implementation in each layer graph, a loss the redesign accepts. Written in `implement`'s options, a plain, `Effect.fn` or built authorizer infers its `action`; defined apart, it is annotated `(action: Action.Any)`.
- **Checks.** An authorizer fails only with a refusal; an operational failure a caller should see, such as a rate limit, is a declared check: `Action.Check` names the one error it may fail with, which `make` adds to the error list of every action listing it, deduplicated, and the request services it may read, one key or a list of keys, each owed per call, declared rather than inferred from the callback's free requirement, so what each call needs is stated with the contract, where a browser-safe declaration can hold it and every surface's types read it; a native layer implements it, `Layer.succeed` with its callback or `Layer.effect` with an Effect building it once per layer graph, which every surface serving a listing action requires at startup; `Action.check`, an alias choosing between the two, is removed. `make` lists each check once, as it does its errors, so a check a spread shared list repeats runs once per call. Checks run after authorization, on public and protected actions alike, in listed order, and may use the call's own `Scope`. This reverses "Hook errors", the unreleased `Refusal | HookErrors<A>`: a hook failing with the union of its actions' declared errors, which an action added without the limit received as a defect on its first limited call, and which took one array spread into each guarded action's `errors` so none was left out. A check declares its error once, on itself, so every action listing it declares the error and every client decodes it, and an action without the check cannot be limited by it. The callback receives the action, never its input: a rule on the input or on one record stays the handler's. Rejected: the spike's free-form operational `before` map beside authorization, two mechanisms for one job; and making authorization a check, which would either let a surface's layer replace an application's permission rule or put that rule into every contract.
- **Toolkit tool ids.** A Toolkit tool's `id` carries the key of what runs a call, its implementation's handlers' memoized layer, which each `implement` makes, so it is unique to the implementation, because Effect finds a tool's handler by its `id`: the `layer` of a `make` call serves any `toolkit` of the same implementations whose tools it serves, one of fewer `actions` included, while two implementations with tools of one name, such as two of one action behind different authorizers, never run each other's handlers. Keyed by the implementation object, a share keeping its hook, an agent's fewer tools, took a layer of its own and isolated nothing: given its source's layer, which the types accept, its first call died on a missing handler. This revises the unreleased key per `make` call, a `Handled` service and then an id suffix, and keeps their stated purpose, each toolkit's handlers its own beside another's with tools of the same names: since the hook moved from a `make` option onto the implementation, a `make` call separates nothing its implementation does not. Keyed per call, a toolkit and a layer of one implementation from two `make` calls type-checked, as `Tool.HandlersFor` is keyed by name, and the first tool call died on a missing handler, so toolkits made per agent or per approval policy could not share one handler layer. Lost: two layers of one implementation, built apart with different services and provided together, each served its own toolkit; now one serves both. Separate services take separate implementations. The key once also held the authorizer's layer's, which told apart nothing the handlers' did not: an authorizer is stated in `implement`, which makes the handlers' layer too.
- **A scope per call.** Each call has a scope of its own, opened by the shared dispatch around the authorizer, the checks and the handler, and `implement` leaves `Scope` out of the request map, as `Action.Check` leaves it out of a check's, so no surface handles it: the CLI's own `Effect.scoped` and its `Exclude` are gone. A Toolkit call held what it acquired until its caller's scope closed, called directly or approved through `LanguageModel`, which runs an approved call in its caller's scope: with a pooled connection per call, a third call on a pool of two waited forever. `runStdio`, each tool and `generateText` also required a `Scope` nothing used. MCP and HTTP already released per call. Opened in dispatch rather than around tool calls alone, the scope covers HTTP too, where a call's finalizers now run before the route middleware resumes and before the success is encoded, not when the request's scope closes; action codecs are service-free, so nothing after the call reads what it acquired. A resource that must outlive a call is the builder's, or a service the host provides around its calls.
- **Approval.** `needsApproval` is one function over every call, `(call, context) =>`, whose `call` is a union by action name, so checking `call.name` narrows `call.input`. This reverses the unreleased per-action option, a function of each action run once by `make` (0a99a00) returning its tool's native approval (0db3f3a), whose input was the union of every action's: `action.name === "erase" ? ## Release

The package publishes to the `latest` tag. The `effect` peer is `~4.0.0`, Effect's 4.0.x
patches: Effect marks every module the surfaces build on (`effect/http`, `effect/http-api`,
`effect/ai`, `effect/cli`, `effect/encoding`) `@stability unstable`, which a minor release may
change, and none `experimental`, which a patch may. The surfaces also rely on behavior of those
modules that no type states: a Toolkit finds a tool's handler by the tool's `id`,
`McpServer.registerToolkit` registers every tool through the registry's `addTool`, and
`HttpApiBuilder.group` lays its build context over each request's. The package is built and
tested against the Effect release in `devDependencies`; `.github/workflows/effect-latest.yml`
runs the full check weekly against the newest 4.x. When that passes on a new minor, widen the
peer's upper bound to admit it, and raise the lower bound only if the package starts to depend on
the newer release. When adopting a newer Effect release for development, bump `devDependencies`
and re-run the full check.

To release: set `version` in `package.json`, add its section to [CHANGELOG.md](CHANGELOG.md)
(every breaking change and how a consumer migrates), commit as `Prepare <version>`, tag
`v<version>`, and push the commit and tag. The tag runs `.github/workflows/npm.yml`, which checks that the tag
matches `version`, repeats the CI checks, and publishes. It authenticates as the package's npm
trusted publisher (this repository and that workflow file, set under the package's npm
settings), so there is no registry token, and npm attaches provenance.
`prepublishOnly` builds; `files` ships `dist` and `docs`. The skill is not in the tarball:
`npx skills add` reads it from GitHub, and agents reading node_modules get `docs/` directly.

## Lint policy

`vite.config.ts` is the source of truth for rule severities; this section explains the
decisions behind it. The vendored plugin's provenance and local corrections are in
[`tools/oxlint/anti-slop/UPSTREAM.md`](tools/oxlint/anti-slop/UPSTREAM.md).

Strict rules are the goal, and lint passes because the code is correct, not because it was
rewritten to satisfy a pattern matcher. A passing lint run is not evidence of type safety by
itself: type safety comes from the compiler flags below and the type-aware `typescript/no-unsafe-*`
rules.

### What is checked

Every owned file: `src`, `tests`, `examples`, `scripts` (including the package-consumer fixture
and `scripts/test-package.mjs`, checked as JavaScript with `allowJs`/`checkJs` and owner-derived
JSDoc types), the plugin regression tests in `tools/oxlint/tests`, and `vite.config.ts`. Lint runs
type-aware with type checking, so `vp check` is one command for format, lint, and compiler
diagnostics.

Excluded: build output (`dist`), agent caches (`.claude`, `.codex`, …), and the vendored plugin
sources under `tools/oxlint/anti-slop`, which follow upstream's own style and are covered by the
regression tests beside them. Nothing owned is excluded to hide findings.

Compiler flags required by policy and set in `tsconfig.json`: `strict`,
`exactOptionalPropertyTypes`, `noUncheckedIndexedAccess`. The assembled package consumer
(`scripts/test-package.mjs`) compiles with the same three flags, so a child configuration does
not weaken them.

### Refactor before making an exception

For each finding:

1. Identify the invariant and who owns it. Does the diagnostic expose a missing boundary, erased
   type information, duplicate validation, or an unnecessary abstraction?
2. Prefer the refactor that removes the cause, even across owned APIs. Update callers and tests
   directly; do not add compatibility wrappers to keep an old shape.
3. Preserve concrete safety: third-party contracts, malformed external input, and runtime
   compatibility survive API changes.
4. Distinguish a rule defect from a legitimate exception. A defect is corrected in the vendored
   rule with a regression test and an `UPSTREAM.md` entry. A legitimate case intentionally caught
   by a broad rule gets the smallest justified exception.
5. Exceptions are line-level (`oxlint-disable-next-line <rule> -- <reason>`) or a tightly bounded
   disable/enable pair. The reason names the boundary and what the operation still guarantees.
   An unused directive is an error (`reportUnusedDisableDirectives: "deny"`).

Never launder a finding: renaming a parameter, dropping an annotation so inference yields `any`,
casting, moving a `typeof` into a one-use helper, or moving code to an unchecked file leaves the
code exactly as unsafe.

### Rule families

- **Unknown and broad inputs** (`no-unknown-parameters`, `no-unknown-returns`,
  `no-unknown-type-aliases`, `no-object-parameters`, `no-unsafe-dictionary-type`): decode at the
  I/O boundary and pass owner contracts inward. There is no name-based exemption; a parameter named
  `cause` is as unknown as any other, and thrown-value boundaries use an explained directive.
- **Evidence loss** (`no-known-value-widening`, `no-chained-type-assertions`, `require-safety-comment-for-type-assertion`,
  `typescript/no-unsafe-type-assertion`): keep inference or validate with `satisfies`. A SAFETY
  comment is necessary, not sufficient; the type-aware assertion rule needs its own explained
  directive when an assertion is a genuine erasure boundary.
- **`any` escape routes** (`typescript/no-unsafe-assignment`, `-argument`, `-call`,
  `-member-access`, `-return`): untyped JSON, SDK generics, callback registries. Type the value at
  its source, for example by importing `package.json` as a typed JSON module instead of parsing it.
- **Runtime probing** (`no-runtime-typeof` with `allowInTypeGuards`): a genuine type predicate may
  probe its subject; discriminating an already typed union takes a narrow explained exception.
- **Quadratic copies** (`no-reduce-accumulator-copy`, `oxc/no-accumulating-spread`): growing copies
  in a loop; fixed-size snapshots may justify an exception.
- **Reflection** (`no-reflect-apply`, `no-reflect-get`): prefer typed access; keep a concrete
  exception only where receiver or getter semantics matter.
- **Module mocking** (`no-module-mocking`): replace dependencies through real seams. The rule
  recognizes `vi` from `@effect/vitest`, this repository's test import, and `vite-plus/test`, as
  well as `vitest`.
- **Compile-failure fixtures** (`tests/types.spec.ts`): an expression under `@ts-expect-error`
  yields an error type, which the `no-unsafe-*` rules see as `any`. Those lines carry a directive
  stating that nothing runs; the fixture's purpose is the compile failure itself.

Off, with reasons recorded beside the setting in `vite.config.ts`:

- `anti-slop/no-array-filter-map`: both forms are linear; rewrites change callback order and
  sparse-array semantics without establishing a performance gain.
- `anti-slop/no-conditional-empty-object-spread`: conditional spread preserves omission semantics
  without mutable builders.
- `anti-slop/no-shape-in-symbol-names`: a substring cannot establish domain ownership; naming is
  reviewed by people.
- `anti-slop/no-widen-then-assert`: the widening is `no-known-value-widening`'s and the narrowing
  assertion `typescript/no-unsafe-type-assertion`'s, which reads types; read from syntax, it took
  a destructured field's evidence from the whole initializer, which its sibling rule corrects.
- `anti-slop-effect/no-service-constructor-imports`: a `make[A-Z]` name cannot establish that an
  import is a dependency-bearing service constructor, and a namespace import bypasses it, which
  rewards the import change the policy calls laundering.

### Verification

- `tools/oxlint/tests/rules.test.ts` runs the corrected rules through Oxlint's `RuleTester`,
  with an accepted and a still-rejected case for each correction.
- `tools/oxlint/tests/configuration.test.ts` runs `vp lint` once on fixtures inside the
  repository, so the probes go through the registered plugin and the effective configuration:
  unknown parameters named `cause`, module mocking via `@effect/vitest`, `typeof` inside and
  outside predicates, literal evidence in destructured bindings, a justified
  `no-unknown-parameters` directive and its unused counterpart, and maintained JavaScript.
  Every other lint, format and type check ignores the fixtures, which hold findings on purpose:
  the run sets `LINT_PROBE`, which lifts their lint ignore pattern in `vite.config.ts`, so a
  `vp check` beside `vp test` never reports them.

### History

Historical measurement, not a backlog: when the baseline was adopted (2026-09-19) the repository
had zero findings under the previous configuration. Enabling the `typescript/no-unsafe-*` rules and
widening coverage to the scripts surfaced 60 findings, all resolved by refactor or by the
explained directives listed above. Two rule-behavior gaps (`cause` exemption, unrecognized
`vite-plus/test` import) and two false positives in `no-known-value-widening` (destructured
bindings inheriting the initializer's evidence, finite mapped keys classified as open
dictionaries) were corrected in the vendored rules.
