# Text field

A contract names no text field: every MCP tool's result is Effect's own, as each revision sends it: on 2026-07-28 the whole encoded success as `structuredContent` and its JSON as one text block, with the success's `outputSchema` listed, where stdio's 2025 revisions send only an object success as `structuredContent` and list only an object-rooted `outputSchema`. This reverses "Text field" as 33493ef recorded it, the contract's `mcp: { text: "markdown" }`, sent raw as the first text block, then the JSON of the rest, without structured content or an output schema, itself the descendant of 0.8.0's `mcp.text` (fd137b5). No consumer outside the library's own tests used it. It rested on a copy of Effect's registry whose `addTool` listed the tool without its `outputSchema` and stripped the native result's `structuredContent`, so it relied on native behaviour no type or doc states: `registerToolkit` registering every tool through `addTool`, `addTool` rebuilding the listing from `...options.tool`, and the native result carrying the structured content to strip. And a result only a client knowing its shape could read: `Testing.mcpClient` decoded only by reading the contract's `text`, and any other client had to know the two blocks. With it go `make`'s type rule for a top-level string field, the startup refusal for one the types could not see, and the client's text decoder. Lost: a body sent once and raw. A consumer sending raw page text, as a downstream app's earlier server sent each 8 KiB page of a fetched document, now sends the page twice, in `structuredContent` and, JSON-escaped twice, in the text block: at least twice its bytes, more for text full of quotes and newlines, which a consumer bounding each result's encoded size must budget for. Effect has no option shaping a toolkit tool's result: `McpServer.registerToolkit` always builds it with structured content and JSON text. The registry's own `addTool`, which a `features` layer reaches on the endpoint's registry, takes any listing and any `CallToolResult`, so a raw-text tool can be registered beside the actions; it is a native feature ("Native MCP features"), not an action: no contract, no authorizer, no other surface, no `Testing.mcpClient` method, and no caller, as only an action's tool promotes the caller's identity, so a raw document that depends on who asks has no supported path. Rejected: keeping the copy until Effect offers a result option, which kept its reliance on unstated native behaviour for an option nobody used; and the option on the server, the unreleased 0.10.0's `tools` (c54210d), which every `Testing.mcpClient` had to repeat, as 33493ef recorded.
