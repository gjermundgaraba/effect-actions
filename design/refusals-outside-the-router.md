# Refusals outside the router

`Authentication.refusalResponse` renders a refusal as authentication answers it, from the same functions: the status and JSON, `no-store`, the 401's challenge and its quoting, RFC 6750's `error_description` and the metadata URL. This partly restores 0.9.0's `protectedResource().challenge()`, removed on the grounds that `make` writes every challenge, which holds for routes only: a caller the router never routes, such as a Node `upgrade` handler admitting a socket, still owes the same answer. The one downstream SDK with such a caller rebuilt the challenge by hand, and its copy had drifted: it escaped nothing, always sent `error_description`, and named the metadata URL without the resource's path. `refusalResponse` returns the whole response rather than a challenge string, since a status and body chosen apart from the challenge is where a copy drifts, and takes the `Authorization` header rather than a flag, so the presented-token rule stays the library's. It is a plain function, not middleware state, so a caller passes the resource and descriptor it gave `layer`, and nothing ties them but that. `make` does not answer through it, as rendering in both places settled each refusal twice. `bearerTokenOf` is exported for a caller holding a header and no request; the canonical example's own reading had drifted. The header has two parsers: routes and MCP read it through Effect's `HttpApiBuilder.securityDecode`, and `refusalResponse`, deciding whether a token was presented, and `bearerTokenOf` through the library's own, which reads it as Effect's `HttpApiSecurity.bearer` does and a test holds equal to `securityDecode`. So `Bearer a b` presents the token `a b`, which RFC 6750 §3.1 counts as `invalid_token`. Rejected: counting `Bearer a b` as no presented token, under which the verifier received `a b` while the challenge said nothing was presented.
