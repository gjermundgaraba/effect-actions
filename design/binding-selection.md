# Binding selection

The binding decides what `ActionHttp.layer` serves: its actions among the implementations given, matched by identity. An implementation's other actions get no route, and their names are not read. `layer` takes the shared `actions` option and leaves out, unbuilt, an implementation holding none of the actions served, as every surface does ("Surface selection"). This reverses c971b1a's refusal of an implementation's action the binding lacks, `Action "x" is not in this HTTP binding`, which made an agent-only tool beside HTTP actions take an implementation of its own, its builder and authorization repeated. Rejected: refusing each implementation holding none of the binding's actions, which made a host filter its implementations per binding. Implementations holding none of them at all are refused, as the wrong implementations or the wrong binding. Lost: a second copy of the contracts module beside a correct implementation is not caught, its action answering 404. A look-alike is not refused by name, which would refuse an HTTP route and an MCP tool of one name from different contracts. Request requirements narrow per implementation; build requirements stay whole, as the builder is built whole. The identity a layer's middleware requires is discharged only where every action the layer serves is protected, a protected handler's always, so a mixed implementation's protected actions take identity-reading middleware in a layer listing them, without being split. A layer serving a protected action requires the named descriptor's provider, `Provider<I, Name>`, type evidence that a verifier, not a startup or request-provided identity, establishes the caller; without the name, a verifier of another descriptor of the same identity satisfied it. This reverses the rejection of such a marker service on the grounds that every custom middleware and test would have to provide it: custom middleware no longer provides identity, and a test provides a verifier rather than a caller.
