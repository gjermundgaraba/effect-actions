# CLI services

A command's services and caller are provided on the command, with `Command.provide`, `Command.provideSync` or `Command.provideEffect`, which wraps only its handler, where help and a parse error never reach. This reverses providing them around the run, as the docs did since cd08952: a layer was built before the arguments were parsed, so `--help` and a mistyped flag opened the database, and a missing identity config failed instead of showing help. The handler decodes the input, so input the schema refuses is refused after the provisions are built. A remote command's static settings are `client`, the options `ActionHttp.client` takes, which `ActionCli.remote` and `ActionCli.remoteCommand` apply to their own requests alone. Rejected: configuring the `HttpClient` for the whole program, which rewrote every request it made, a login request's too, and put the API's credentials on each; and taking no client options, which had every remote CLI prepend its URL by hand. Settings read when a command runs stay on an `HttpClient` provided on the command, since `transformClient` returns a client failing only with `HttpClientError`, so a `Config` read in it would have to die. One aggregate is one connection, so its subcommands take no `client`. Effect's own behavior: an aggregate run alone builds its provisions before showing help, and fails instead if one fails.
