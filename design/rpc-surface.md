# RPC surface

Actions are served as Effect RPC by `ActionRpc`: a browser-safe binding, `ActionRpc.make(actions, { authentication, error })`, holding a native `RpcGroup` of one rpc per action, served by `ActionRpc.layer(binding, implementations, { middleware })` on Effect's own `RpcServer`, over a protocol the host provides, and called by `ActionRpc.client(binding)`, with the methods of `ActionHttp.client` and `Action.client`. The server runs a copy of the group whose payloads, successes and errors are the actions' JSON encodings, decoded by the library after authentication and the layer's middleware, because Effect's protocol decodes a payload first and answers one that does not decode with a defect, before any middleware runs: bad input would be an untyped failure, and a protected rpc's input would be read before its caller is known. So protocols speak JSON alone, as deferring decoding needs a payload readable without its schema, and `layer` refuses to build under one whose codec is not JSON: schema-binary's writes a payload in its schema's own layout, which only that schema reads, and the protocol reads it before any middleware runs, so a server of any codec, its rpcs' schemas unknown, still fails there; the codec is what it checks, not a content type's name; lost are binary payloads and their size. The layer's `middleware` is native `RpcMiddleware`, server-only, failing only with the binding's `error`, which every rpc declares so clients decode it, as `ActionHttp.layer` takes its middleware and `ActionHttp.make` its errors; rejected, middleware on the binding, which would put server middleware in the module a browser imports. Request-time services, such as a tenant, are router request requirements, as over HTTP: a listed middleware provides them per message on any protocol, and router middleware around a router-mounted protocol per HTTP request, or per connection over a WebSocket; a startup service never does. Authentication is per message, from the rpc's headers with the descriptor's native scheme, so one WebSocket carries several callers, and a browser, which sets no header on its upgrade, sends its token on each message; a refusal is the typed `Unauthenticated` or `Forbidden`, with no challenge, step-up or `Cache-Control`, which belong to HTTP responses. Public and protected actions are served over any protocol: `Authentication.layer` requires the `HttpRouter` only to publish a protected resource, so a socket or stdio server authenticates each message as a WebSocket does, though a verifier's request services come only from a router-mounted protocol's route, since authentication runs before the layer's middleware. Rejected for now: stdio as a local surface whose host provides the identity, as `ActionMcp.runStdio` does. The server's rpcs carry no native middleware: each handler runs the authentication and the layer's middleware itself, each step as the call runs, then decodes the input, since Effect applies native middleware as it sets a call up, outside any Effect, so a middleware that throws would fail the whole connection, and a payload would be decoded before its authentication. One boundary around each call logs anything its rpc does not declare, a defect of the verifier, a middleware or the handler, an undeclared failure, or a declared failure or a success that does not encode, reports it once with its real cause to the call's `ErrorReporter`s, and answers it as that request's defect, an `Error` whose message is `Internal server error`, never failing the connection's other calls (`disableFatalDefects`), since the native server would send the cause's message to the caller. Effect's server reports every failed call too, to the reporters of the call's context, which lies over the layer's, and cannot be kept from them, so the boundary encodes the failure itself, the first of a cause, and fails with its JSON marked `ErrorReporter.ignore`, Effect's own convention for expected errors, not enumerable so never sent: what is checked is what is sent, and a declared failure is never reported, as over HTTP, where it is a response; rejected, marking the built-in errors and asking applications to mark theirs. `ActionRpc.client` exists because the native client, `RpcClient.make(binding.group)`, still works but takes `{}` for an action without input and is shaped unlike every other client; rejected, the native client alone. Streaming rpcs stay out, as actions are unary. This reverses no recorded decision; the package's stated scope, "It is not Effect RPC", changes with it, and so do two invariants: a browser client may import `ActionRpc`, and Effect through `effect/rpc`, and the native servers and clients the surfaces build on include `RpcServer` and `RpcClient`.
