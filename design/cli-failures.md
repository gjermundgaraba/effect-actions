# CLI failures

A CLI command fails with Effect CLI's `CliError.UserError`, whose `cause` is the action's failure and whose message is the JSON HTTP sends for it, so `Command.run` prints it on stderr and a program runs on the stock `NodeRuntime.runMain`. This reverses fe492ed's "A CLI encodes nothing, so it declares no errors": `runMain` printed a command's failure on stdout with a stack and none of its fields, such as a `Forbidden`'s `scopes`. `Failure` is a type export only, since `instanceof` an exported generic class narrows to `Failure<any>`. A failure no schema encodes, a builder's or the transport's, prints its tag or an error's name and the message of it and each cause, never other fields, since a builder's error may hold a connection string; a message alone dropped the refused connection beneath an `HttpClientError`. No plain object's `name` is read, which may be a field like any other. Rejected: `Cause.prettyErrors`, which prints a failure that is not an `Error`, a plain object or a `Data.TaggedClass`, as its JSON, every field included. A success that does not encode is a defect, as over HTTP: the handler broke its contract, and a typed `SchemaError` read as the caller's mistake. Rejected: the library printing each failure and marking it reported, which a host could neither restyle nor switch off, as it can a `UserError` through `CliOutput`'s formatter and `renderErrors: false`, and which would mark the host's own error objects. A `Failure`'s `reason` is its `cause`, as Effect names a tagged error's nested one, so a host matches it with `Effect.catchReason("UserError", "UserNotFound", f)`; the parser's `UserError`, with no `reason`, falls through. Cost: Effect's `ReasonTags` reads a tag only where every reason of the union has one, so a builder failing with a plain `Error` leaves `catchReason` no tag. Rejected: an `ActionCli.catchFailure(tag, f)` of our own, which repeats the native combinator.
