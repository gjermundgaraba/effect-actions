# Native MCP features

An endpoint serves Effect's own resources, prompts and tools passed as its `features`, built in the endpoint's fresh graph so they register on its registry, which stays per endpoint: each native helper provides `McpServer.layer` itself, so merged beside the endpoint it registers on a registry no endpoint serves. Rejected: the endpoint providing its `McpServer` for the host to compose with `Layer.provide`, which `runStdio`, a program, cannot; and dropping the fresh graph, which shares one registry among every endpoint of a graph. Features are native: no authorizer runs for them, and on an endpoint naming an authentication descriptor every request a feature answers authenticates ("One MCP URL"). They register before the actions, which refuse a native tool of an action's name, since Effect's registry keeps one tool per name and it replaced the action's tool, and with it the access decided by that name, a public action's anonymous one included. Features read only their build context, as `resource` and `prompt` replace a request's, so content that depends on the caller is an action. Rejected: wrapping the registry, which each native helper's own `McpServer.layer` bypasses and whose request services Effect's handlers replace inside; restoring them takes Effect's `resource` and `prompt` merging the request's context as `Toolkit.handle` does, to be raised upstream. The native tool registry is mutable, so each endpoint and each stdio server gets its own, `Layer.fresh` around the registry alone: handlers are provided outside it, so builders stay shared, as do the services the features need, provided around the endpoint. A tool's JSON Schema has a `$ref` at its root resolved, as MCP requires an object root, and its definitions as `$defs`.
