# In-process client

`Action.client` calls implementations in process with `ActionHttp.client`'s shape, one method per action taking its input directly, so moving between an in-process and a remote caller changes the line acquiring it. A call fails with what an HTTP client decodes as values, the action's errors and the built-in ones, and with nothing of a transport: input that does not pass is `InvalidInput`, as an HTTP client's is before it sends anything (until input rules moved into contract schemas, an HTTP client failed it with the native `SchemaError`, which a caller could not tell from an answer that does not decode), and a binding's errors are its middleware's, which no handler fails with. Input, success and failure each pass through their JSON codec, encoded to JSON text then decoded, as a wire carries them, a failure through every error its action declares, the built-in ones included, so the handler receives, and the caller gets, what a remote call's would: an undeclared field dropped, a class instance built anew, a decoding transformation such as a trim applied. A success or a failure that does not encode or decode, an error the action does not declare included, is a defect, as it is an empty 500 over HTTP: its `SchemaError`, then a failure itself, which the `SchemaError` does not name. Each codec runs as an Effect, as HTTP's does, so one that completes later passes; run synchronously, it died. A success that does not is a defect on the CLI too, which prints a failure no schema encodes by name, since a builder's or the transport's is one; a call's failure never is, since a client builds when it is acquired and has no transport. A failure is mapped within its cause, which keeps the span it failed in, and takes the stack of the error it replaces: failed anew, its trace would start at the codec. Checking the type side alone (`Schema.toType`) would hand the handler the caller's own values, untrimmed, and pass a success whose encoding fails, and passing a failure on as it is would keep a trimmed field untrimmed and type an undeclared error, so a test through the client would pass where every surface differs or fails. The cost is paid in production too: every call encodes its input, and its success or failure, to JSON text and decodes it, work linear in the value's size that a direct call skips, small beside a handler's own I/O, and the price of a caller that gets what a remote one would. Each method owes per call what the handler and the authorizer read, and a protected action's identity whether or not they read it, provided around the call, and the acquisition owes only the builders' startup services and a `Scope`, failing as they fail, as `Layer.build` does. Captured at acquisition, the caller of a client acquired in a builder or a layer would be a startup identity, which the invariants forbid, and one client would serve one caller. A call reads its caller's context alone. HTTP and `Toolkit.handle` lay their build context beneath a request's (3a4275c); a client does not lay the acquisition's beneath a call's, where a caller provided around the acquisition would reach every call its types say owes one, and a span around the acquisition would parent every call made outside one. Acquisition builds into the memo map of the layer graph around it, `Layer.CurrentMemoMap`, as `HttpRouter` builds a middleware's dependencies, or into a map of its own under none, so a builder acquiring a client shares each builder's one run with the surfaces of its graph, whichever builds first; a fork, as `Layer.build` makes, runs it twice when the acquiring builder builds first. A local CLI command still builds per invocation (79e02ce): an invocation is one call, where a client serves many. `actions` lists fewer of the implementations' actions, as a surface's does. It lives in `Action`, beside the implementations it calls, and imports no transport: the call rule every client shares, `Call` and `inputOf`, lives apart from the HTTP client, and `tests/browser.test.ts` checks `Action`'s imports.
