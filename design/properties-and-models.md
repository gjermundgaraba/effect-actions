# Properties and models

A rule that holds over many inputs is a property, `it.prop` or `it.effect.prop`, over inputs `Arbitrary.schema` derives from the schemas involved, and behavior that depends on earlier calls is a model: generated command sequences, `Arbitrary.array`, checked against a small model of what each step should do. The expected value comes from the generated input or the model, never from the code under test nor another surface's answer, and a new one is proven by a planted violation: the code broken, the property failing with its shrunk counterexample, the code restored. An example test stays for one interface between components, and for a rule whose oracle would restate the code, as a name pattern's would. The seeds are `tests/guarantees/surfaces-agree.test.ts`, every surface answering a generated input and a generated declared failure as JSON carries it, and `--flag=value` carrying any text; `tests/guarantees/builds.model.test.ts`, builders run once per layer graph across generated surfaces, selections and arrangements, and each call's resources released when it ends; and `tests/stdio/console.model.test.ts`, the stderr console writing what Node's console writes for generated command sequences. Planted, they caught a projection trimming strings or dropping empty fields over MCP, RPC and the CLI, a CLI number read in plain decimals only, a `countReset` clearing every label, and a counter's label read as a format string, which no example test caught. Lost: about five seconds of test time, and generators to maintain beside the schemas. Rejected: rewriting the example suites as properties wholesale, which trades the readable cases the docs and design notes cite for churn; and generating inputs whose expected value another surface supplies, which agrees with itself whatever is wrong.
