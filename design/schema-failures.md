# Schema failures

Schema failures take no policy. Input that does not decode is the built-in `InvalidInput`, or the native invalid-arguments answer over MCP and the Toolkit, so no application declares an error for it; a success that does not encode is a defect, an empty 500 over HTTP. This reverses 0.6.0's `schemaError` policy, `invalid` or `internal`: such a success means the handler broke its contract after it ran, so any write it made has happened, which a declared error would misreport, and defects, crashes and proxies send a 5xx without a declared body anyway. `InvalidInput` lists the failure's `issues`, each `{ path, message }`, which a handler may name too: an application kept a second error for bad input only because the built-in one carried a string, so a client matched two tags for one fault. The field defaults to empty when the class is built, so a refusal with a message alone stays valid, and is always sent, so the OpenAPI document and every decoder require it. This reverses its optional field, added in bc3951f with `fromSchemaError`, which made code reading it check for it on every `InvalidInput` but `fromSchemaError`'s; empty says the same, and is always there to read. MCP and the Toolkit keep their native answers, which have no field for it.
