# Media fields

An action's success may carry media: `Action.Image`, a schema of `{ data: Uint8Array, mimeType: string }`, as a top-level field of a struct success, optional or an array, or as the whole success or an array of it. An optional array field is refused, as its blocks cannot tell absent from empty, and so is media anywhere else when `layerHttp` or `runStdio` is called: nested, in a union or record, in a class or a struct with its own encoding, or given an encoding of its own, which would send it as something other than its media, in an input or error. Every surface but MCP sends it as JSON, the bytes in base64, as Effect's JSON codec encodes a `Uint8Array`. An MCP tool lifts each media field out of its result into a content block of its own, after the JSON text, in field order, and sends the rest as it sends any success: `structuredContent` is the encoded success without its media fields, `outputSchema` describes that, and the one text block is its JSON, exactly. A success that is media, or whose every field is, sends its blocks alone, without structured content, text or output schema. Each block lifted from a field names it in its `_meta`, `"effect-actions/field"`, on every revision, a whole success's blocks none, and `Testing.mcpClient` reassembles the success by it: blocks matched in order are ambiguous where two array fields of one kind are adjacent, and refusing those would be another rule; a client not knowing the key ignores it, as MCP's `_meta` is open. A model reads an image only from a content block, and a tool returning one was a native feature, registered with `addTool`, with no contract, no authorizer, no other surface and no `Testing.mcpClient` method ("Native MCP features"). Measured on 2026-10-08 against Claude Code 2.1.294, two runs each, on 2025-11-25 and on 2026-07-28 through `runStdio`: the model read an image beside `structuredContent`, with and without an `outputSchema`, beside text alone, and alone; where `structuredContent` was present it received that and not the text block, whose marker never reached it, so the text must mirror the structured content and can carry nothing of its own. Text is no kind: a string field stays in the structured content and its copy, as Claude Code drops every text block beside structured content, a raw document among them, and lifting text would cost a tool its structured output for a body sent once; if escaped markdown proves to read worse, `Action.Text` can be added as a kind sent as content alone, without changing images, beside the planned `Action.Audio`, `Action.Resource` and `Action.ResourceLink`. Effect's `registerToolkit` builds every success as `structuredContent` and one JSON text block and takes no option, so `ActionMcp` registers every tool itself through the registry's public `addTool`, from the same `Toolkit`: one path, for tools with media and without. This is not what "Text field" rejected, a proxy of the registry `registerToolkit` writes to, stripping a result it did not build and relying on behaviour no type states; here the registration is ours, built from public exports. Costs: about 160 lines of code following `registerToolkit`, its decode options, failure classification, defect scrubbing, listing, and the request services it omits from the handlers' retained context and the context it registers in, which the native server lays over every call's ("Handler requirements", "A scope per call"), re-read on every Effect patch and pinned by a test comparing ours with the native listing and results for tools without media, the 2025 revisions' unquoted string success included, which Effect's protocol adapters apply to any result; about 130 lines of code for the lifting rules, the refusal's walk of every served schema and `Testing.mcpClient`'s reassembly; Effect's private `toolJsonSchema`, rebuilt from `Schema.toJsonSchemaDocument`; the Toolkit still encodes the whole success, so a tool's bytes are encoded to base64 once and discarded, as the shared tool definition every surface uses encodes them; a Toolkit sends media to a model as base64 text, since Effect's providers stringify a tool's result, and `ActionToolkit` does not refuse such an action, which its `actions` leaves out, until Effect's `Prompt.ToolResultPart` carries media; Mastra's MCP client, by its source, drops images from a tool listing an `outputSchema` (not measured). The name is `Action.Image`, which reads at the use site; `Action.ImageContent` would repeat MCP's name and suit `Action.Resource` less. Rejected: a hook in Effect, proposed as `Tool.ContentRenderer` in Effect-TS/effect#8316 and withdrawn, Effect putting result policy in its protocol adapters instead (#8468); an MCP projection on the contract, `mcp: { content }`, untyped for every client, whose text a client showing `structuredContent` never shows, as measured; a content-block success, MCP's shape on every surface with no structured data beside it; a `resource_link` to bytes served as a resource, read differently by every client and a resource each application serves; and media in `structuredContent` too, every byte sent twice.
