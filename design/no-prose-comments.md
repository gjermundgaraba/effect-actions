# No prose comments

Code carries no prose comments: `no-comments/no-prose-comments`, the repository's own rule in `tools/oxlint/no-comments/`, reports each one. What a comment said a thing is goes into a name or a type; why goes into a test title, a design note or the commit message. Two kinds remain. A line directive with its reason after `--`: `// @ts-expect-error -- <reason>` and `// oxlint-disable-next-line <rule> -- <reason>`; an unsafe type assertion's directive states the invariant that makes it hold. And JSDoc in `src/`, which `vite.config.ts` allows there with the rule's `allowJsDoc` option: the build keeps each module its own file, every `.d.mts` ships, and a consumer's editor shows a declaration's JSDoc on hover, through a public module's re-export too. A re-export's own JSDoc is never shown: the declarations merge every re-export into one `export { … }` and drop it, so the private declaration carries the consumer's text. `examples/` is exempt, as an example is a doc snippet whose comments explain it where a consumer reads it. This reverses the rule that implementation rationale belongs in code comments: agents copy comments, so one explaining a workaround spreads the workaround, and nothing checks a comment against the code beside it, so it drifts, where a name is read at every use, a test fails and a note is cited by title (rat-stack's rule, after Lauren Tan's). It also drops the `SAFETY:` comment `require-safety-comment-for-type-assertion` required above an assertion: nearly every one sat above a `typescript/no-unsafe-type-assertion` directive justifying the same assertion, so its text moved into the directive's reason, and the rule is off. With no maintained JavaScript left, no file outside `src/` needs JSDoc for its types. Lost: the reason beside the line it explains; a reader follows a name, a test or a note to it. And in `src/` the ban rests on a comment's form: `//` and `/* */` are reported, while JSDoc on a private function or a local passes. Rejected: rat-stack's full ban, which strips the JSDoc consumers read in their editors and leaves `docs/` the only reference; keeping JSDoc only where the published declarations carry it, which no rule of positions can tell: the build keeps JSDoc on the members of an exported object literal whose type is inferred and drops it from the parameters of a function passed to a call, so such a rule was wrong in both directions, took a walk of the syntax tree to state, and made `export` what licensed a comment on a private module's declaration; keeping JSDoc only in the PascalCase public modules, which strips the docs of the types they re-export from private ones; and an autofix, which deletes the reason with the comment.
