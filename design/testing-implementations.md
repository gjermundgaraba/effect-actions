# Testing implementations

An implementation's own behavior is tested in process, with `Action.client`, and a surface's under `Testing.layer`, which keeps what only the wire shows: authentication, statuses, codecs as sent, MCP results. This reverses b0dc80a's testing of handlers through a surface alone, under which a test had one caller per layer, and a tool-only action needed a binding of its own. Under `Testing.layer` the routes keep their descriptor's provider, a real or test verifier, and each client sends its caller's token, so several callers share one layer. A command built with `Command.make` that calls a client is the host's own: the authorizer runs, but not ActionCli's output rules, so a failure it leaves as it is prints on stdout with a stack and without its fields. The docs prefer a derived command wherever `name`, `positional` and `render` express the syntax, and otherwise map the failure to Effect CLI's `CliError.UserError`. Rejected: a helper giving native commands ActionCli's failures, a second way to build what `ActionCli.command` and `ActionCli.remoteCommand` build, for commands whose output is the host's anyway.
