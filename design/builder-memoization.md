# Builder memoization

A builder stays a layer Effect memoizes, built once per layer graph, and nothing checks where it is built. `HttpRouter.serve`, `Testing.layer` and `HttpRouter.provideRequest` fork the memo map, and a fork builds what its parent has not, so a job merged beside `serve` may build a builder the routes build again, with services of its own; `Layer.mergeAll` builds its layers concurrently, so whichever build reaches the memo map first decides. An application's own stateful service splits the same way, which no builder design reaches, so the docs state one rule for both: with one server, everything the process runs goes in the layer it serves; otherwise `Action.layer` and the shared services go above the server and its siblings. `Layer.fresh` gives a surface a build of its own, and a route whose handler calls a toolkit takes the toolkit's layer with `Layer.provide`, not `provideRequest`, for one build with the routes. Rejected: an `Action.layer` every host with a builder must provide, which forces the layer to exist but not where it goes, leaves the application's services split, repeats implementation lists in every host, test and toolkit program, types two implementations of the same names alike, and sets layer surfaces apart from `runStdio` and the CLI; `Action.layer` providing built handlers that surfaces prefer to their own build, which builds twice where it is provided beside the surfaces or to only one of them, and would have the CLI reuse it, reversing 79e02ce; reading the root memo map through the fork's parent, a field outside Effect's `MemoMap` interface; a warning when two builds of one implementation are live, which parallel tests, `Layer.fresh` surfaces and a CLI beside a server set off legitimately; and 0.8.0's build per surface, which builds twice an implementation HTTP and MCP both serve.
