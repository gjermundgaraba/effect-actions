# ActionCluster

Import `@gjermundgaraba/effect-actions-cloudflare/ActionCluster`. An application on Cloudflare declares its entities with the core's `ActionEntity`, as on any cluster runtime, and runs them on `@effect/platform-cloudflare`'s Cloudflare runtime, through the Worker [ActionWorker.md](ActionWorker.md) makes: each entity id is one Durable Object, named `CloudflareCluster.encodeName(type, id)` in the `ClusterEntity` namespace, holding the entity's mailbox, its stores and its events in the object's own SQLite database. `ActionCluster.layer(options)`, which `ActionWorker.make` builds the application over, is that runtime's layer, `CloudflareCluster.layer`, with one change: its entity clients send a volatile call's headers as the caller set them, so a credential `ActionEntity.reaching` forwards reaches the entity, which authenticates it, and a persisted tell's redacted, as its envelope is kept at rest. Its JSDoc holds the rules.

## Serve the entities from the Worker

The Worker serves every entity's actions and events itself, `ActionHttp.layer(RoomHttp, ActionEntity.reaching(Room))`, each call sent to the object its input's key names, and one MCP endpoint for all of them, `requestScoped`, in [`chat-rooms/src/routes.ts`](../examples/chat-rooms/src/routes.ts). Each entity id builds its own stores as it activates, in `ActionEntity.layer`'s `services`: there, `ActionCluster.Sql` is the object's own database, `@effect/platform-cloudflare`'s `DurableObjectSqlClient`, and `ActionCluster.layerObject` provides it as `SqlClient` with `Stored.layerEvents` over it, beneath the example's message store and webhooks; built outside an activation, it dies. `ActionWorker.make` and `ActionCluster.Sql` wrap the runtime's experimental APIs, so an application needs no lint exception for them. A room reads its name from `Entity.CurrentAddress` the same way.

## Answer a call made through an entity's client

A Worker route that calls an entity's client itself, `Entity.client`, `ActionEntity.client` or `ActionEntity.nativeClient`, outside `ActionEntity.reaching`, answers a failed call's cause with `ActionCluster.failureResponse(cause)`: a 503 with `Retry-After: 1` where the entity could not be reached or did not answer in time, a 499 where the request's client went away, and otherwise a 500, the cause logged. Its JSDoc holds the rules.

## Read the object's own state

An entity that needs more of its Durable Object than its database, such as a library taking the object's `storage`, or `waitUntil` to keep the object alive for work that outlives the call that started it, reads `ActionCluster.ObjectState.orDie`: the object's `id`, `storage`, `waitUntil` and `abort`, in its build, its `services`, a handler or a fiber either forks, on an object of `ActionWorker.make`'s `ClusterEntity`, which records it as the object is made. A library written with Promises that takes the object's SQLite storage, as `{ sql, transaction }`, gets `state.database`, one object per build of the entity's handlers, whose `transaction` takes the gate the runtime's mailbox writes wait on. Two traps are the runtime's, and its JSDoc holds them with the rest: a transaction opened on `storage` directly skips that gate, so another call's reply can be lost to its rollback; and the runtime owns the alarm, so `storage.setAlarm` replaces what it scheduled.

## Deliver a room's events by webhook

A protected event the Worker serves through `ActionEntity.reaching` is delivered by webhook from the entity its input names, as the core's `docs/ActionEntity.md` says. Each room builds `Webhook.layer` in its `services`, with `persist`, in [`chat-rooms/src/routes.ts`](../examples/chat-rooms/src/routes.ts), over a table of its own in the object's database and fetch's client, in [`chat-rooms/src/platform/webhook-delivery.ts`](../examples/chat-rooms/src/platform/webhook-delivery.ts), and `Login` names a `schema`. `resolveCallbacks: false` checks a literal callback address alone, as a Worker has no resolver. Each retry wait is a tell on the object's alarm, so an evicted room is built again to deliver. `MessagePosted` is `notified`, so a subscribed room asks it again only when a post notifies it, and hibernates while idle. [`chat-rooms/test/webhooks.test.ts`](../examples/chat-rooms/test/webhooks.test.ts) answers the deliveries through Miniflare's `outboundService`, given in `vite.config.ts`.

## Test on workerd

`@cloudflare/vitest-plugin` runs the Worker, its four classes and their storage in workerd; [`chat-rooms/test/worker.test.ts`](../examples/chat-rooms/test/worker.test.ts), with [`test/support.ts`](../examples/chat-rooms/test/support.ts), calls the Worker's `fetch` through `FetchHttpClient`, reads an object's tables with `runInDurableObject`, evicts one with `evictDurableObject`, and plants a failure with a SQLite trigger. `deliverNow` delivers a scheduled wake early by moving its `deliver_at` in `cluster_messages` and running the object's alarm with `runDurableObjectAlarm`: those columns of `cluster_messages`, `deliver_at`, `processed` and `envelope`, are the runtime's private schema, not its API, so a test reading them is rechecked on an upgrade of `@effect/platform-cloudflare`.

## What differs from another cluster runtime

- **The runtime owns each object's alarm**, waking it for a scheduled tell, a replay or `Entity.keepAlive`: an application sets none of its own, though `ActionCluster.ObjectState`'s `storage` would let it, and schedules its work with the core's `ActionEntity.wakeAt`, run by the layer's `onWake`.
- **An object is built per wake.** The runtime evicts an idle object, and the next request builds the entity again, `services` and builders included: anything in memory is gone, the database stays.
