# Guarantees

Rules that hold across every surface. Module pages state what is their own and link here for the rest.

## Dependency lifetimes

- Handlers receive decoded input, return decoded results, and may fail only with their action's declared errors and the built-in ones. Anything else is a defect.
- Build-time services are those yielded in the builder Effect passed to `implement`, or in an Effect building its hook. Each is a layer Effect memoizes. Within one layer graph it runs once, however many surfaces serve its implementation (HTTP layers, MCP endpoints, a Toolkit) and however many implementations `Action.share` its builder, and its scope is the host's. A share given a hook of its own builds that hook once, and never its source's.
- `HttpRouter.serve` and `Testing.layer` each build their routes in a layer graph of their own, which reuses what the host has already built but shares nothing it builds itself: a builder's run, a built hook, a service of your own such as an in-memory store. `HttpRouter.provideRequest` also builds the layer it provides in a graph of its own, which reuses what the routes' graph has already built. So one rule places builders and your own services alike: **with one server, put everything the process runs in the layer it serves**, a job or an agent beside the routes included; **otherwise, provide `Action.layer(implementations)` and the services they share above the server and its siblings**, such as a second server, a program running beside it, or several `Testing.layer`s. A sibling given neither builds a builder, and a service whose layer both provide, a second time, with state of its own, whenever the server's graph builds it first, which depends on the order `Layer.mergeAll` lists them in.
- `Action.layer` builds each builder first, once for every surface and client below it, with the services it is given. Building it acquires every supplied implementation's builder, including implementations no surface serves. Without it, a builder runs only for a surface serving its implementation, or a client of it.
- A builder runs again only in a separately built layer graph, such as a second `Testing.layer`. A local `ActionCli` command is the exception: it builds the selected implementation, its hook included, per invocation, even where the host already built it, and releases it after the call, once the handler's and the hook's own finalizers have run.
- Acquiring an `Action.client` builds its implementations into the layer graph it is acquired in, as a layer of it: in a builder or a layer, the host's graph, where it shares each builder's one run with every surface of that graph, whichever builds first; in a program, the graph of a layer provided around it, which every client acquired there shares; under none, a graph of its own. What it builds stays until its scope closes and nothing else in the graph holds it. Acquired per request, in a handler, it builds for every call unless a surface of the graph serves the same implementation, and its builders' startup services become that handler's request requirements: acquire it where builders live.
- **Without `Action.layer`, the builder runs with whichever surface's services Effect builds it with first.** Services provided around one surface reach the others too, and so does an `Action.layer` provided to one surface alone: provide its startup services once, to `Action.layer` above every surface that serves it. To give an HTTP or MCP surface a build and startup services of its own, wrap it in `Layer.fresh`, which builds everything inside it anew, and provide what the surfaces share, authentication included, outside it. A Toolkit's tools run on one build of their implementation, whatever layers of it are provided ([ActionToolkit.md](ActionToolkit.md#rules)): separate services take separate implementations.
- Request-time services are those yielded inside a handler or the hook itself. For HTTP-hosted surfaces (`ActionHttp`, `ActionMcp.layerHttp`) they appear as `HttpRouter.Request<"Requires", X>`, one for each service `X`, and are supplied by router middleware around the surface, authentication included, `HttpRouter.provideRequest`, or request context. For `ActionToolkit`, `ActionCli`, `ActionMcp.runStdio` and `Action.client` the host supplies them at invocation; a client's call reads them from its caller's context alone, never from what the client was acquired with.
- Each call has a scope of its own, on every surface: what the hook and the handler acquire is released when the call ends, the handler's first, before its result is encoded, and over HTTP before the route middleware resumes. A Toolkit call is no exception, whether `tools.handle` makes it or `LanguageModel` runs it, approved or not, and neither is an `Action.client` call. `Scope` is never a request-time requirement. A resource that must outlive a call is the builder's, or a service the host provides around its calls.
- Use distinct tags for build-time capabilities and request-scoped identity. Everything in a call's context wins over what the surface was built with under the same tag: what authentication, other router middleware, `HttpRouter.provideRequest` or a Toolkit's caller provides, and what the server runs in, as provided around `HttpRouter.serve`, `Testing.layer` or the program. A value provided to one surface's layer only fills in a service or reference the call lacks; to give one surface's requests their own, such as a log level or an `ErrorReporter`, use `HttpRouter.provideRequest` on its layer. So never provide an identity or tenant tag in a server's startup layer or root context: every route no authentication covers would serve its callers as that identity. In memory, one `Testing.layer` is one caller, whose identity a test provides around it; authentication among its routes still provides its own ([Testing.md](Testing.md#one-caller)). Types verify presence, not provenance.

## Authorization

- An implementation carries its hook: `Action.implement(actions, handlers, before)`. Every surface serving it runs the hook. No surface takes a hook of its own, so none can leave it out.
- Leaving the hook out never grants access: `implement` requires one, and `share` keeps its source's unless given another ([Action.md](Action.md#implementations)). An implementation without an action-level rule states `Action.allowAll`: every caller the surface admits may call.
- `before` runs once per call, after input decodes, before the selected handler and outside its span. It runs on `ActionHttp`, `ActionMcp` over HTTP and stdio, `ActionToolkit`, a local `ActionCli` command, and `Action.client`. There is no per-action opt-out; calling a handler function directly bypasses dispatch, so call it through `Action.client`.
- Authentication establishes identity for remote callers. It is router middleware, such as `Authentication.make`, that the host provides around the HTTP surfaces it covers (`ActionHttp.layer`, `ActionMcp.layerHttp`). It runs before decoding and provides the identity to the hook and handlers.
- A handler or hook that reads identity requires that identity service in the types of every HTTP surface serving it. The host must supply it through authentication on protected requests. Wrap every layer that must authenticate callers, even if its handlers and hook need no identity. On a local surface the host supplies the identity. Under `Action.allowAll`, dispatch performs no action-level authorization.
- The hook receives the selected action contract, typed as the implementation's own actions, so a policy reads `action.access` or `action.name` instead of a hand-maintained list. It is not authentication: authentication establishes identity, then the hook authorizes what that identity may do.
- It fails with a refusal, `Action.Unauthenticated` or `Action.Forbidden`, or with an error every action of its implementation declares, such as a rate limit; anything else is a type error. Every surface declares the refusals and each action's own errors, so a hook's failure is encoded like a declared error: HTTP sends its JSON with its status, 401 or 403 for a refusal, MCP an `isError` tool result, the Toolkit a returned failure, a CLI command the same JSON on stderr. A step-up refusal under `Authentication.make` is the one exception, below; no other failure steps up.
- A CLI command fails with Effect CLI's `UserError`, whose `cause` is what the hook fails with. Every local command may fail with the action's errors and `Action.BuiltIn`, whatever its implementation's hook ([ActionCli.md](ActionCli.md#rules)).
- The services the hook yields are request-time requirements, like a handler's, and they join the surface's request context. A local caller (`ActionCli`, `ActionToolkit`, stdio, `Action.client`) supplies them itself. What an Effect building the hook yields: [dependency lifetimes](#dependency-lifetimes).
- A step-up refusal is one an OAuth client acts on: `Unauthenticated`, or a `Forbidden` naming `scopes`. On a route `Authentication.make` covers, `ActionHttp`'s or `ActionMcp.layerHttp`'s, it answers the request with its HTTP status, 401 or 403, its JSON and its challenge, whether the hook or a handler fails with it.
- Over MCP that answer replaces the tool result, as MCP authorization defines, unless a handler's notification already started the response ([ActionMcp.md](ActionMcp.md#rules)). Without `Authentication.make` there is no OAuth client to step up: it is answered like a declared error, and the model reads it.
- A `Forbidden` naming scopes carries the `insufficient_scope` challenge an OAuth client re-authorizes on ([Authentication.md](Authentication.md#rules)). A `Forbidden` naming no scopes is always answered like a declared error.
- Map another service's refusals before failing with them. A handler or hook calling another service through a client that decodes the built-in errors, such as `ActionHttp.client`, gets that service's `Unauthenticated` or `Forbidden` as a value any handler may fail with; passed on as it is, it is this server's own refusal. Under `Authentication.make` it steps up: a caller whose token is valid is sent to sign in again, its 401 naming `invalid_token`, or to re-authorize for the other service's scopes. Map it to an error the action declares, or to a defect.
- All surfaces decode input before dispatch. Invalid input skips the hook and handler, so unauthorized callers can receive schema errors (HTTP's `InvalidInput` message describes the input's schema). To refuse a caller before decoding, use authentication or other native HTTP middleware around the surface; the `before` hook runs too late for that.
- A limit on callers, such as a rate limit or a quota, goes in one of two places. After decoding, on every surface: the hook, failing with an error every action of its implementation declares, spread from one array into each action's `errors`; an action added without it is a type error. Before decoding, over HTTP only: router middleware around the routes, answering with an error of the binding's `errors` ([ActionHttp.md](ActionHttp.md#binding-errors)). Input that does not decode never reaches the hook, so only middleware counts it.
- A limit's state, such as a rate limiter's counts, is a startup service of a built hook ([Action.md](Action.md#built-hooks)), provided once, to `Action.layer` above every surface: it is built once per layer graph, and every surface counts against it. Yielded in the hook itself, it is a request-time requirement, and `HttpRouter.provideRequest` builds one for each layer it is provided to: HTTP and MCP provided apart count apart.
- Authentication must establish identity on every protected request. Types cannot verify that a handler performed authorization; the `before` hook is the one place the library guarantees runs before the handler, so put action-level authorization there. A check on one record, such as whether this actor may rename this user, needs the input and its data: make it in the handler's data access.
- `access` is contract metadata, required on every action and kept as a literal type. It is a tool's read-only hint, the default `destructive` hint and the `action.access` span/log annotation, but enforces no authorization. A hook can switch on what an action does instead of on its name.

## Wire behavior

HTTP is a native `HttpApi`; MCP is a native `McpServer` with one `Tool` per action. The
built-in errors are `Action.InvalidInput` (400), `Action.Unauthenticated` (401) and
`Action.Forbidden` (403), each `{ _tag, message }`.

| Case                        | HTTP                                                                                                    | MCP                                                                                                                                                                  |
| --------------------------- | ------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Input                       | decoded with the schema's JSON codec; failure is **400** `InvalidInput`, `message` the schema issues    | decoded with the schema's JSON codec; failure is an `isError` result from 2025-11-25 on, and a JSON-RPC `InvalidParams` error before                                 |
| Success                     | the success codec's encoding as the body: `{"id":"1","name":"Ada"}`, `42`                               | `structuredContent: <encoded>` and its JSON as text on 2026-07-28; earlier stdio revisions structure only an object, or nothing ([ActionMcp.md](ActionMcp.md#rules)) |
| Declared error              | encoded by its schema with its `httpApiStatus` (unannotated: 422): `{"_tag":"UserNotFound","id":"x"}`   | `isError: true`; text content is the same JSON; no `structuredContent`                                                                                               |
| `before` failure            | its JSON with its status, **401** / **403** for a refusal, after input decoding; the handler never runs | the same `isError` result, after arguments are decoded; under `Authentication.make` a step-up refusal is **401** / **403**                                           |
| Invalid output encoding     | a defect: empty **500**                                                                                 | `isError: true`, text `Tool execution failed due to an internal server error.`; cause logged, not sent                                                               |
| Defect                      | empty **500**                                                                                           | same generic `isError` result; cause logged, not sent                                                                                                                |
| Unknown path or method      | 404                                                                                                     | another path: 404, as HTTP; another HTTP method on the endpoint: an empty **405** with `Allow: POST`; an unknown tool: a JSON-RPC `-32602` error, with 200 over HTTP |
| Invalid JSON / content type | 400 `InvalidInput` / 415 for a missing or non-JSON type                                                 | over HTTP, a JSON-RPC `Parse error` (`-32700`) with 200 / an empty **415** for a missing or non-JSON type; over stdio, a line that is not JSON goes unanswered       |

- An MCP endpoint's text field changes only its tool's success result and listing ([ActionMcp.md](ActionMcp.md#rules)): the field is sent raw, first, then the JSON of the rest, without structured content, and the tool lists no `outputSchema`. HTTP, OpenAPI, the HTTP client, the Toolkit and the CLI serve and describe the whole success, and the tool's other outcomes are answered as in this table.
- The HTTP surfaces set no header of their own; handler failures are ordinary declared error responses. Under `Authentication.make`, a `Forbidden` naming scopes carries `WWW-Authenticate: Bearer error="insufficient_scope", scope="..."`.
- `Authentication.make` marks every response of the routes it covers `Cache-Control: no-store`, unless its route states its own caching. A covered route stating its own says `private` unless its answer is the same for every caller: a credential a proxy forwards is invisible to a cache in front of that proxy. It gives every 401 among them without a challenge its own, whether authentication, a hook or a handler answers it. As a protected resource, it names its metadata URL in every challenge, and a 401's names `scopesRequired`, and `invalid_token` when the request presented credentials ([Authentication.md](Authentication.md#rules)).
- A 401 carries a challenge only under `Authentication.make`, which is bearer authentication. Native middleware authenticating a session cookie answers its own 401, and sets `Cache-Control: no-store` itself ([Authentication.md](Authentication.md#rules)).
- Routes are `POST <prefix>/<action>`; the prefix defaults to `/api`. Operation IDs are the action names. Effect generates OpenAPI component names and references.
- Effect reads each request body whole, with no size limit unless the host sets one: provide `Layer.succeed(HttpServerRequest.MaxBodySize, ByteSize.mebibytes(1))` to `HttpRouter.serve`'s layer. The limit covers every route on the server, MCP endpoints and the host's own routes included, except a body a route reads as a stream. Node's server (`NodeHttpServer`) closes the connection of a request over it without a response. `HttpRouter.toWebHandler` ignores it: limit bodies in the platform serving the handler.
- Every HTTP endpoint and every tool declares `InvalidInput`, `Unauthenticated` and `Forbidden` beyond the action's own errors, and an endpoint its binding's too, so typed callers decode them. Any handler may fail with them; no action or binding lists them, and no error of its own may reuse their tags.
- They are produced by decoding, by authentication, by a hook, or by any handler. Errors reachable from one endpoint have distinct `_tag`s, because the client decodes a status by trying the schemas declared for it: `Action.make` refuses an action whose errors share one, and `ActionHttp.make` an action whose error shares one with its binding's, so no server or client of them meets one. A built-in error is always tried first, so a loose schema of an action's, such as `Schema.Struct({ message: Schema.String })`, never captures one.
- HTTP refuses undeclared input fields, nested ones too, as the OpenAPI document's `additionalProperties: false` says: the request is a 400 `InvalidInput` naming the field's path. A client drops them when it encodes, since TypeScript lets a wider value through. A record accepts every key its key schema does. A CLI command refuses them too, with an `InvalidInput`, in `--input` and in a flag's JSON. A Toolkit drops them, as Effect decodes a model's tool call. An action without input, `input: {}` given or not, accepts only `{}`, on every surface; over HTTP, an empty JSON body is a 400. MCP tools are strict (`Tool.Strict`): undeclared arguments are invalid arguments, an `isError` result from 2025-11-25 on and a JSON-RPC `InvalidParams` error on earlier stdio revisions. An input that declares its fields publishes `additionalProperties: false` in its schema over HTTP and on stdio from 2025-06-18 on, and not on the revisions before ([ActionMcp.md](ActionMcp.md#rules)).
- A message for input that does not decode says what the schema expects and, where Effect's decoder reports one, each issue's path; never a value sent, on every surface: `InvalidInput` over HTTP, from a CLI command and from `Action.client`, MCP's invalid-arguments result, a Toolkit's `ToolParameterValidationError`. A path names each key it passes through, an undeclared key and a record's keys included, so a record keyed by an email or a token names it. Effect CLI's own parser, which reads a flag before the schema decodes it, names a rejected choice, an unknown flag or an unexpected argument as typed. A schema's own `message` annotation, or a filter's message, is sent as written, so never put the input in one. Declare a secret `Schema.Redacted`, so what a handler logs of its decoded input prints `<redacted>`; a tool call's span holds it all the same ([observability](#observability)).
- A CLI command prints the success's encoding on stdout, and a failure on stderr as the JSON HTTP sends: the action's declared error, a binding's, a built-in one, `InvalidInput` included. A success that does not encode is a defect there too, which the command does not print ([ActionCli.md](ActionCli.md#rules)).
- An `Action.client` call passes its input, its success and its failure through their JSON codecs, encoded then decoded, as HTTP carries them, so its handler and its caller get what a remote call's would. A success or a failure that does not pass, an error its action does not declare included, is a defect, as it is an empty 500 over HTTP ([Action.md](Action.md#clients)).

## Names

- Action names are unique within one HTTP binding; two bindings with different prefixes may reuse one, but then cannot be combined into one `HttpApi`. A tool is named after its action, so action names are also unique within each Toolkit or MCP endpoint that serves them, and kebab-case command names within each aggregate CLI command. A client's method is too, so they are unique within each `Action.client`.
- Surfaces validate only the names they serve. HTTP does not check tool names; MCP does not check route names.
- MCP, a Toolkit, `ActionCli.make` and `Action.client` expose every action of the implementations passed to them. `ActionHttp.layer` exposes the actions its binding holds among them, and `ActionCli.command` only its selected action. Builder acquisition follows the [dependency lifetimes](#dependency-lifetimes), including explicit `Action.layer` prebuilding and per-invocation CLI selection.
- Surfaces match an implementation to a contract by object identity, never by name. `ActionHttp.layer` refuses an implementation holding none of its binding's actions, and serves no action its binding does not hold, whatever its name; `ActionCli.command` refuses an action with no implementation in its list.

## Observability

- Each handler runs in a span named after its action, a child of the transport's request span, or of its caller's through `Action.client`, with attributes `action.name` and `action.access`. Every log line the handler writes carries the same two annotations. Names are unique per binding; the request span's route tells two bindings' same-named actions apart. The pre-handler hook, decoding and encoding happen outside the handler span.
- MCP defects and encoding failures are logged with their cause and answered generically.
- Over `ActionHttp` and `ActionMcp.layerHttp`, a handler's defect reaches the `ErrorReporter`s provided to the surface's layer once.
- Every MCP tool call, over HTTP and over stdio, and every Toolkit call runs through Effect's `Toolkit.handle`, which records the call's arguments as sent on the current span, as the attribute `parameters`: a tracer the host installs receives them, a `Schema.Redacted` field's value included, which a handler's logs print `<redacted>`. HTTP records no request body. Where a tracer exports spans, keep an action that takes a secret off tools ([Action.md](Action.md#contracts)).

## Scope

What the package does, and nothing else:

- HTTP means JSON `POST` endpoints built on Effect's `HttpApi`. It is not Effect RPC.
- MCP means one native `McpServer` `Tool` per action over HTTP or stdio; supported revisions follow [ActionMcp.md](ActionMcp.md#rules). There is no MCP SDK runtime dependency.
- Actions are unary: one decoded input, one decoded success or one declared error. No streaming, uploads, prompts, resources, retries, or code-execution sandbox.
- Authentication and authorization are the application's. The library supplies the seams:
  - `Authentication.make`, native router middleware for identity;
  - one `before` hook for the authorization rule, bound to an implementation and run by every surface, `Action.allowAll` where there is none;
  - `access`, for what a rule reads;
  - the built-in refusals every caller decodes.
- It defines no scopes and no verifier: a refusal names the scopes a call lacks, and the library answers with the OAuth challenge. Tool discovery is not filtered by actor. Production needs real token validation, request limits, and error reporting.
