# Guarantees

Rules that hold across every surface. Module pages state what is their own and link here for the rest.

## Dependency lifetimes

- Handlers receive decoded input, return decoded results, and may fail only with their action's declared errors and the built-in ones. A failure the types let through anyway, such as from plain JavaScript or a cast, is answered as the [wire table](#wire-behavior) says for an undeclared failure.
- Build-time services are those yielded in the builder Effect passed to `implement`, in an Effect building its authorizer and in a verifier's `Authentication.layer`. Each is a layer Effect memoizes. Within one layer graph it runs once, however many surfaces serve its implementation (HTTP layers, MCP endpoints, a Toolkit) or list its actions, and its scope is the host's. Two `implement` calls are two builders, even of one builder Effect: each runs once per graph.
- `HttpRouter.serve` and `Testing.layer` each build their routes in a layer graph of their own, which reuses what the host has already built but shares nothing it builds itself: a builder's run, a built authorizer, a service of your own such as an in-memory store. `HttpRouter.provideRequest` also builds the layer it provides in a graph of its own, which reuses what the routes' graph has already built. So one rule places builders and your own services alike: **with one server, put everything the process runs in the layer it serves**, a job or an agent beside the routes included; **otherwise, provide `Action.layer(implementations)` and the services they share above the server and its siblings**, such as a second server, a program running beside it, or several `Testing.layer`s. A sibling given neither builds a builder, and a service whose layer both provide, a second time, with state of its own, whenever the server's graph builds it first: `Layer.mergeAll` builds its layers concurrently, so whichever build reaches the memo map first decides, not the order it lists them in.
- `Action.layer` builds each builder first, once for every surface and client below it, with the services it is given. Building it acquires every supplied implementation's builder, including implementations no surface serves. Without it, a builder runs only for a surface serving its implementation, or a client of it.
- A builder runs again only in a separately built layer graph, such as a second `Testing.layer`. A local `ActionCli` command is the exception: it builds the selected implementation, its authorizer included, per invocation, even where the host already built it, and releases it after the call, once the handler's and the authorizer's own finalizers have run.
- Acquiring an `Action.client` builds its implementations into the layer graph it is acquired in, as a layer of it: in a builder or a layer, the host's graph, where it shares each builder's one run with every surface of that graph, whichever builds first; in a program, the graph of a layer provided around it, which every client acquired there shares; under none, a graph of its own. What it builds stays until its scope closes and nothing else in the graph holds it. Acquired per request, in a handler, it builds for every call unless a surface of the graph serves the same implementation, and its builders' startup services become that handler's request requirements: acquire it where builders live.
- **Without `Action.layer`, the builder runs with whichever surface's services Effect builds it with first.** Services provided around one surface reach the others too, and so does an `Action.layer` provided to one surface alone: provide its startup services once, to `Action.layer` above every surface that serves it. To give an HTTP or MCP surface a build and startup services of its own, wrap it in `Layer.fresh`, which builds everything inside it anew, and provide what the surfaces share, authentication included, outside it. A Toolkit's tools run on one build of their implementation, whatever layers of it are provided ([ActionToolkit.md](ActionToolkit.md#rules)): separate services take separate implementations.
- Request-time services are those yielded inside a handler or the authorizer itself. For HTTP-hosted surfaces (`ActionHttp`, `ActionMcp.layerHttp`, `ActionRpc.layer`) they appear as `HttpRouter.Request<"Requires", X>`, one for each service `X`, and are supplied by router middleware around the surface, `HttpRouter.provideRequest`, or request context; for `ActionRpc.layer` also by its listed `middleware`, the only source over stdio or a socket server, and over a WebSocket router middleware runs once for the upgrade, so once per connection ([ActionRpc.md](ActionRpc.md#rules)). A protected action's identity is the exception: only its authentication provider supplies it, so the layer requires that provider instead, and nothing else provided stands in for it. For `ActionToolkit`, `ActionCli`, `ActionMcp.runStdio` and `Action.client` the host supplies them at invocation, the identity of every protected action included, whether or not anything reads it; a client's call reads them from its caller's context alone, never from what the client was acquired with.
- Each call has a scope of its own, on every surface: what the authorizer and the handler acquire is released when the call ends, the handler's first, before its result is encoded, and over HTTP before the route middleware resumes. A Toolkit call is no exception, whether `tools.handle` makes it or `LanguageModel` runs it, approved or not, and neither is an `Action.client` call. `Scope` is never a request-time requirement. A resource that must outlive a call is the builder's, or a service the host provides around its calls.
- Use distinct tags for build-time capabilities and request-scoped identity. Everything in a call's context wins over what the surface was built with under the same tag: what authentication, other router middleware, `HttpRouter.provideRequest` or a Toolkit's caller provides, and what the server runs in, as provided around `HttpRouter.serve`, `Testing.layer` or the program. A value provided to one surface's layer only fills in a service or reference the call lacks; to give one surface's requests their own, such as a log level or an `ErrorReporter`, use `HttpRouter.provideRequest` on its layer. So never provide an identity or tenant tag in a server's startup layer or root context: a protected route still requires its authentication provider, and a public handler or a native route reading the tag would serve every caller as that identity. In memory, a test serves protected routes behind an authentication provider, the real one or a test verifier of the same descriptor, and each client sends its own caller's credential ([Testing.md](Testing.md#signed-in-callers)). Types verify presence, not provenance, for every service but a protected action's identity.

## Authorization

- A contract states who may call it, `caller`: `Action.Anyone`, or the identity service a caller must have. Every surface enforces it, whatever the handler and the authorizer read. A remote surface, `ActionHttp.layer`, `ActionMcp.layerHttp` or `ActionRpc.layer`, names the contracts' authentication descriptor (`authentication: Login`), and its layer requires that descriptor's provider, `Authentication.layer`, which verifies each protected request's credential and provides the identity. A local surface requires the identity per call, in the types, and a call that lacks it anyway, as plain JavaScript may, fails with `Unauthenticated` before the authorizer runs. No surface takes an authorization policy of its own, so none can leave one out or loosen it.
- A call runs, in order: authentication, then over HTTP and RPC the layer's own `middleware` ([ActionHttp.md](ActionHttp.md#rules), [ActionRpc.md](ActionRpc.md#rules)), then input decoding, then the authorizer, for a protected action only, then the handler. Each step refuses before the next runs. Over HTTP and MCP a protected request is authenticated before its body is read: without a credential, a protected route answers 401 before a 415 or a 400, and a protected tool's call 401 before its arguments are decoded. Over RPC each message of a protected rpc is authenticated before its payload is decoded. On a local surface, the identity is checked after decoding.
- An implementation of protected actions states its authorizer, `Action.implement(actions, handlers, { authorize })`: leaving it out is a type error, and plain JavaScript leaving it out throws at `implement`. `Action.allowAll` lets every authenticated caller call. An implementation of public actions alone takes none, a type error too, and plain JavaScript passing one throws at `implement`. The authorizer never runs for a public action, even one implemented beside protected ones.
- The authorizer runs once per call, after input decodes, before the handler and outside its span. It runs on `ActionHttp`, `ActionRpc`, `ActionMcp` over HTTP and stdio, `ActionToolkit`, a local `ActionCli` command, and `Action.client`. There is no per-surface override: a caller trusted on one surface, such as an admin CLI's operator, is an identity the host supplies there, which the same authorizer admits ([ActionCli.md](ActionCli.md#trusted-callers)). Calling a handler function directly bypasses dispatch, so call it through `Action.client`.
- The authorizer receives the selected action contract, typed as the implementation's own, so a policy reads `action.readOnly` or `action.name` instead of a hand-maintained list. It is not authentication: authentication establishes identity, then the authorizer decides what that identity may do. It fails only with a refusal, `Action.Unauthenticated` or `Action.Forbidden`: any other failure is a type error, and a limit on callers is the handler's. HTTP sends a refusal's JSON with 401 or 403, RPC fails the call with it, typed, MCP an `isError` tool result, the Toolkit a returned failure, a CLI command the same JSON on stderr. A step-up refusal on a remote surface is the one exception, below.
- The services the authorizer yields are request-time requirements, like a handler's, and they join the surface's request context. A local caller (`ActionCli`, `ActionToolkit`, stdio, `Action.client`) supplies them itself. What an Effect building the authorizer yields: [dependency lifetimes](#dependency-lifetimes).
- A CLI command fails with Effect CLI's `UserError`, whose `cause` is what the authorizer or the handler fails with. Every local command may fail with the action's errors and `Action.BuiltIn` ([ActionCli.md](ActionCli.md#rules)).
- A step-up refusal is one an OAuth client acts on: `Unauthenticated`, or a `Forbidden` naming `scopes`. Step-up is Bearer's and protected actions': on a protected route of `ActionHttp`, or a protected tool's call on an `ActionMcp.layerHttp` endpoint naming a Bearer authentication descriptor, it answers the request with its HTTP status, 401 or 403, its JSON and its challenge, whether authentication, the authorizer or a handler fails with it. Over HTTP it answers the refusal as it leaves the layer's `middleware`: one that recovers from it keeps its own response, and one that turns it into another error the binding declares answers with that error. A public route's or a public tool's refusal never steps up, signed in or not: over HTTP its JSON with its status, over MCP an `isError` tool result. RPC never steps up: every refusal is the call's typed failure, with no status and no challenge.
- Over MCP that answer replaces the tool result, as MCP authorization defines, unless a handler's notification already started the response ([ActionMcp.md](ActionMcp.md#rules)). On an endpoint without authentication, or naming a descriptor of another scheme, there is no OAuth client to step up: it is answered like a declared error, an `isError` tool result the model reads, and over HTTP its JSON with its status, without an `insufficient_scope` challenge. A refusal of the authentication itself is still its 401 or 403.
- A `Forbidden` naming scopes carries the `insufficient_scope` challenge an OAuth client re-authorizes on ([Authentication.md](Authentication.md#rules)). A `Forbidden` naming no scopes is always answered like a declared error.
- Map another service's refusals before failing with them. A handler calling another service through a client that decodes the built-in errors, such as `ActionHttp.client`, gets that service's `Unauthenticated` or `Forbidden` as a value any handler may fail with; passed on as it is, it is this server's own refusal. On a remote surface it steps up: a caller whose token is valid is sent to sign in again, its 401 naming `invalid_token`, or to re-authorize for the other service's scopes. Map it to an error the action declares, or to a defect.
- Input decodes before the authorizer. Invalid input skips it and the handler, so a caller the authorizer would refuse can receive schema errors (HTTP's `InvalidInput` message describes the input's schema), as can any caller of a public action. To refuse a caller before decoding, over HTTP or RPC only, use the layer's `middleware`, inside authentication, or over HTTP router middleware around the surface: [ActionHttp.md](ActionHttp.md#rules), [ActionRpc.md](ActionRpc.md#rules).
- A limit on callers goes in one of three places. After decoding, on every surface: the handler, failing with an error its action declares, the limiter a startup service its builder yields, so every surface of the graph counts against one ([Action.md](Action.md#implementations)). Before decoding, over HTTP or RPC only: the layer's own `middleware`, which runs after authentication and so may key the limit by the caller, or over HTTP router middleware around the routes, which runs before authentication; either answers with an error of the binding's `error` ([ActionHttp.md](ActionHttp.md#binding-errors), [ActionRpc.md](ActionRpc.md#rules)). Input that does not decode never reaches a handler, so only middleware counts it, and a protected request without a valid credential reaches only router middleware.
- Types cannot verify that a verifier checks what it should, or that an authorizer states the right rule: the authorizer is the one place the library guarantees runs before the handler of a protected action, so put action-level authorization there. A check on one record, such as whether this actor may rename this user, needs the input and its data: make it in the handler's data access.
- `readOnly` is contract metadata, required on every action and kept as a literal type. It is a tool's read-only hint, a read-only tool's default `destructiveHint` and the `action.read_only` span/log annotation, but enforces no authorization. An authorizer can switch on what an action does instead of on its name.

## Wire behavior

HTTP is a native `HttpApi`; MCP is a native `McpServer` with one `Tool` per action; RPC is a native `RpcServer` with one rpc per action. The
built-in errors are `Action.InvalidInput` (400), `Action.Unauthenticated` (401) and
`Action.Forbidden` (403), each `{ _tag, message }`; an `InvalidInput` also lists `issues`, empty
when it names none, and a `Forbidden` may add `scopes`.

| Case                        | HTTP                                                                                                  | MCP                                                                                                                                                                                                                                            |
| --------------------------- | ----------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Input                       | decoded with the schema's JSON codec; failure is **400** `InvalidInput`, `message` the schema issues  | decoded with the schema's JSON codec; failure is an `isError` result from 2025-11-25 on, and a JSON-RPC `InvalidParams` error before                                                                                                           |
| Success                     | the success codec's encoding as the body: `{"id":"1","name":"Ada"}`, `42`                             | `structuredContent: <encoded>` and its JSON as text on 2026-07-28; earlier stdio revisions structure only an object ([ActionMcp.md](ActionMcp.md#rules)); a media field is lifted into a block of its own ([ActionMcp.md](ActionMcp.md#media)) |
| Declared error              | encoded by its schema with its `httpApiStatus` (unannotated: 422): `{"_tag":"UserNotFound","id":"x"}` | `isError: true`; text content is the same JSON; no `structuredContent`                                                                                                                                                                         |
| Authentication              | a protected route without a valid credential: **401** with a challenge, before its body is read       | a request a protected tool's call or a native feature needs: **401** with a challenge, before its body is read ([ActionMcp.md](ActionMcp.md#rules))                                                                                            |
| Authorizer refusal          | its JSON with its status, **401** / **403**, after input decoding; the handler never runs             | the same `isError` result, after arguments are decoded; on a Bearer-authenticated endpoint a protected tool's step-up refusal is **401** / **403**                                                                                             |
| Invalid output encoding     | an empty **500**, reported to `ErrorReporter`s                                                        | `isError: true`, text `Tool execution failed due to an internal server error.`; cause logged, not sent                                                                                                                                         |
| Defect                      | empty **500**                                                                                         | same generic `isError` result; cause logged, not sent                                                                                                                                                                                          |
| Unknown path or method      | 404                                                                                                   | another path: 404, as HTTP; another HTTP method on the endpoint: an empty **405** with `Allow: POST`; an unknown tool: a JSON-RPC `-32602` error, with 200 over HTTP                                                                           |
| Invalid JSON / content type | 400 `InvalidInput` / 415 for a missing or non-JSON type, after authentication on a protected route    | over HTTP, a JSON-RPC `Parse error` (`-32700`) with 200 / an empty **415** for a missing or non-JSON type; over stdio, a line that is not JSON goes unanswered                                                                                 |

- RPC answers as HTTP decodes, without statuses or headers: input decoded with the schema's JSON codec, a failure the typed `InvalidInput` with its `issues`; a success its encoding; a declared error, a refusal included, the call's typed failure, encoded by its schema; a defect, an undeclared failure, or a success or a declared failure that does not encode, that request's defect, an `Error` whose message is `Internal server error`, its cause logged, the connection's other calls unaffected ([ActionRpc.md](ActionRpc.md#rules)).
- The HTTP surfaces set no header of their own; handler failures are ordinary declared error responses. On a route a Bearer descriptor authenticates, a `Forbidden` naming scopes carries `WWW-Authenticate: Bearer error="insufficient_scope", scope="..."`.
- Authentication marks every response to a request it authenticates, on a protected HTTP route, an MCP endpoint naming a descriptor or a route of the host's own under `Authentication.protect`, `Cache-Control: no-store`, unless its route states its own caching, such as `private, max-age=31536000, immutable` for a content-addressed download. A covered route stating its own says `private` unless its answer is the same for every caller: a credential a proxy forwards is invisible to a cache in front of that proxy, which may store the answer and serve it to anyone. A failure that enclosing middleware serializes always gets `no-store`, whatever caching it states. An MCP endpoint's answer to a request it does not authenticate, discovery, its listing or a public tool's call without a credential, gets none, as a public HTTP route's does: it reads no credential. It gives every 401 among them without a challenge its scheme's, where the scheme has one, whether authentication, the authorizer or a handler answers it, a failure that enclosing middleware serializes included. As a protected resource, it names its metadata URL in every challenge, and a 401's names `scopesRequired`, and `invalid_token` when the request presented credentials ([Authentication.md](Authentication.md#rules)).
- A 401 carries a challenge only on a route authentication covers, and only where its scheme has one: Bearer's, an `Http` scheme naming itself, or Basic's with its realm, the descriptor's name. An API key's 401 is the same JSON and `Cache-Control: no-store`, without a challenge ([Authentication.md](Authentication.md#rules)).
- Routes are `POST <prefix>/<action>`; the prefix defaults to `/api`. Operation IDs are the action names. Effect generates OpenAPI component names and references.
- Effect reads each request body whole, with no size limit unless the host sets one: provide `Layer.succeed(HttpServerRequest.MaxBodySize, ByteSize.mebibytes(1))` to `HttpRouter.serve`'s layer. The limit covers every route on the server, MCP endpoints and the host's own routes included, except a body a route reads as a stream. Node's server (`NodeHttpServer`) closes the connection of a request over it without a response. `HttpRouter.toWebHandler` ignores it: limit bodies in the platform serving the handler.
- Every HTTP endpoint, every rpc and every tool declares `InvalidInput`, `Unauthenticated` and `Forbidden` beyond the action's own errors, and an endpoint or an rpc its binding's too, so typed callers decode them. Any handler may fail with them; no action or binding lists them, and no error of its own may reuse their tags.
- They are produced by decoding, by authentication, by an authorizer, or by any handler. A client decodes a status by trying the schemas declared for it, as it decodes any union: errors sharing a `_tag` are told apart by their other fields, the first that decodes winning, so make them disjoint, by a literal field for one. A built-in error is always tried first, so a loose schema of an action's, such as `Schema.Struct({ message: Schema.String })`, never captures one.
- HTTP refuses undeclared input fields, nested ones too, as the OpenAPI document's `additionalProperties: false` says: the request is a 400 `InvalidInput` naming the field's path. A client drops them when it encodes, since TypeScript lets a wider value through. A record accepts every key its key schema does. RPC refuses them too, with an `InvalidInput` naming the field. A CLI command refuses them too, with an `InvalidInput`, in `--input` and in a flag's JSON. A Toolkit drops them, as Effect decodes a model's tool call. An action without input, `input: {}` given or not, accepts only `{}`, on every surface; over HTTP, an empty JSON body is a 400. MCP tools are strict (`Tool.Strict`): undeclared arguments are invalid arguments, an `isError` result from 2025-11-25 on and a JSON-RPC `InvalidParams` error on earlier stdio revisions. An input that declares its fields publishes `additionalProperties: false` in its schema over HTTP and on MCP ([ActionMcp.md](ActionMcp.md#rules)).
- An `InvalidInput` for input that does not decode lists `issues`, one `{ path, message }` per issue its `message` describes: `path` holds the keys and indexes from the input's root, `["lines", 1, "count"]`, a symbol key as its string form, `Symbol(name)`, and is empty for the input as a whole. Over HTTP a wrong or missing top-level literal field is such an issue, reported as the whole expected shape. A handler failing with `InvalidInput` may give `issues` of its own, sent as written, and `issues: []` without them: the field is always sent, and the OpenAPI document requires it. MCP's and a Toolkit's native answers have a message only.
- A message for input that does not decode says what the schema expects and, where Effect's decoder reports one, each issue's path, as does each of an `InvalidInput`'s `issues`; never a value sent, on every surface: `InvalidInput` over HTTP, from a CLI command and from `Action.client`, MCP's invalid-arguments result, a Toolkit's `ToolParameterValidationError`. A path names each key it passes through, an undeclared key and a record's keys included, so a record keyed by an email or a token names it. Effect CLI's own parser, which reads a flag before the schema decodes it, names a rejected choice, an unknown flag or an unexpected argument as typed. A schema's own `message` annotation, or a filter's message, is sent as written, so never put the input in one. Declare a secret `Schema.Redacted`, so what a handler logs of its decoded input prints `<redacted>`; a tool call's span holds it all the same ([observability](#observability)).
- A media field, `Action.Image`, is JSON on every surface but MCP: `{ "data": "<base64>", "mimeType": "image/png" }`, the bytes in base64, as Effect's JSON codec encodes a `Uint8Array`. HTTP sends it so, a CLI command prints it so, a Toolkit gives it so to a model, and `Action.client` passes it through that codec. Only an MCP tool lifts it, into an image block beside the rest of the success ([ActionMcp.md](ActionMcp.md#media)).
- A CLI command prints the success's encoding on stdout, and a failure on stderr as the JSON HTTP sends: the action's declared error, a binding's, a built-in one, `InvalidInput` included. A success that does not encode is a defect there, which the command does not print ([ActionCli.md](ActionCli.md#rules)).
- An `Action.client` call passes its input, its success and its failure through their JSON codecs, encoded then decoded, as HTTP carries them, so its handler and its caller get what a remote call's would. A success or a failure that does not pass, an error its action does not declare included, is a defect, as it is an empty 500 over HTTP ([Action.md](Action.md#clients)).
- A failure an action does not declare, which the types refuse but plain JavaScript or a cast lets through, is answered by each surface its own way: `Action.client` dies with a defect, HTTP answers an empty 500, MCP its internal-error tool result, `Tool execution failed due to an internal server error.`, a local CLI command fails with `UserError` whose `cause` is that failure, and a Toolkit call fails with an `AiError`, `Failed to encode result`. Declare every error a handler may fail with.

## Names

- Action names are unique within one HTTP or RPC binding; two HTTP bindings with different prefixes may reuse one, but then cannot be combined into one `HttpApi`. A tool is named after its action, so action names are also unique within each Toolkit or MCP endpoint that serves them, and kebab-case command names within each aggregate CLI command. A client's method is too, so they are unique within each `Action.client`.
- Surfaces validate only the names they serve. HTTP does not check tool names; MCP does not check route names.
- `ActionHttp.layer`, `ActionRpc.layer`, MCP, a Toolkit and `ActionCli.make` expose the actions their `actions` option lists, or every action of the implementations without it, `ActionHttp.layer` and `ActionRpc.layer` only those their binding holds; `ActionCli.command` exposes only its selected action. `Action.client` exposes every action of the implementations passed to it. A selected action keeps its implementation's authorizer, and its builder's one run. Selection never changes policy: an action's `caller` and authorizer are the same wherever it is served. Builder acquisition follows the [dependency lifetimes](#dependency-lifetimes), including explicit `Action.layer` prebuilding and per-invocation CLI selection: a surface's `actions` leaving out every action of an implementation leaves that implementation unbuilt.
- Surfaces match an implementation to a contract by object identity, never by name. `ActionHttp.layer` and `ActionRpc.layer` refuse implementations holding none of their binding's actions, and serve no action their binding does not hold, whatever its name; an `actions` option refuses a listed action the binding does not hold, or none of the implementations holds, or `ActionCli.remote` one its binding does not, marking one of a held name as another contract; `ActionCli.command` refuses an action with no implementation in its list.
- An `actions` option narrows a surface's types only where it is always given. Options whose `actions` may be absent, an optional property or a union with options lacking it, serve every action when it is absent and the listed ones when given, so their types owe what every action owes; `Action.client` offers methods, and `ActionToolkit.make` tools, only for the actions such options may list, which it has either way. An explicit type argument names the options' type, not the actions, and requires the options argument: `ActionMcp.layerHttp<typeof app, { readonly actions: readonly [typeof Status] }>(...)`. A misspelled option is a type error on every surface, beside `actions` too, and in any member of a union of options. A CLI's `commands` key naming no action of the binding or the implementations is refused; one naming an action the list leaves out is unused, so one record serves aggregates of several selections.
- A list of actions is typed by its members, on every surface and in `Action.byName`: `[A, B]` holds `A` and `B`. A list narrowed at runtime, such as an `Array` of a union, a filtered list or a conditional element, is still typed as holding every member, and what it does not hold is absent where it is read: `byName` has no entry for it, a client no method, and `implement` refuses its handler, `Unknown handlers: <name>`. Build a list from the contracts themselves.

## Observability

- Each handler runs in a span named after its action, a child of the transport's request span, or of its caller's through `Action.client`, with attributes `action.name` and `action.read_only`, a boolean. Every log line the handler writes carries the same two annotations. Names are unique per binding; the request span's route tells two bindings' same-named actions apart. Authentication, decoding, the authorizer and encoding happen outside the handler span.
- MCP and RPC defects and encoding failures are logged with their cause and answered generically; over RPC, as that request's defect alone.
- Over `ActionHttp`, `ActionMcp.layerHttp` and `ActionRpc`, a handler's defect reaches the call's `ErrorReporter`s once, and a declared failure never does: those around the server, as provided to `HttpRouter.serve` or `Testing.layer`, or else those provided to the surface's layer, as any service resolves ([dependency lifetimes](#dependency-lifetimes)).
- Every MCP tool call, over HTTP and over stdio, and every Toolkit call runs through Effect's `Toolkit.handle`, which records the call's arguments as sent on the current span, as the attribute `parameters`: a tracer the host installs receives them, a `Schema.Redacted` field's value included, which a handler's logs print `<redacted>`. HTTP records no request body. Where a tracer exports spans, keep an action that takes a secret off tools ([Action.md](Action.md#contracts)).

## Scope

What the package does, and nothing else:

- HTTP means JSON `POST` endpoints built on Effect's `HttpApi`.
- RPC means one rpc per action on Effect's `RpcServer`, over protocols speaking JSON only; protected actions over the HTTP and WebSocket protocols ([ActionRpc.md](ActionRpc.md#rules)).
- MCP means one native `McpServer` `Tool` per action over HTTP or stdio; supported revisions follow [ActionMcp.md](ActionMcp.md#rules). There is no MCP SDK runtime dependency.
- Actions are unary: one decoded input, one decoded success or one declared error. No streaming, uploads, prompts, resources, retries, or code-execution sandbox.
- Authentication and authorization are the application's. The library supplies the seams:
  - `caller` on each contract, enforced by every surface;
  - `Authentication.make` and `Authentication.layer`, a named declaration of one native scheme, Bearer by default, and its verifier, enforced and documented with native endpoint security;
  - one `authorize` for the authorization rule, bound to an implementation of protected actions and run by every surface, `Action.allowAll` where there is none;
  - `readOnly`, for what a rule reads;
  - the built-in refusals every caller decodes.
- It defines no scopes and no verifier: a refusal names the scopes a call lacks, and the library answers with the OAuth challenge. A descriptor names one native scheme, Bearer by default: a session cookie, an API key or Basic is the descriptor's scheme, which its verifier receives decoded. OAuth, its challenges, discovery and step-up, is Bearer's. One identity per action, and one per remote surface. Tool discovery is not filtered by actor. Production needs real token validation, request limits, and error reporting.
